# API platform

`identity/local-account-mail.ts` posts one approved synthetic invitation to the fixed Cuevo Mailpit capture endpoint. It validates the deliberate fragment-only account continuation, caps response bytes, sends bilingual text and returns only capture acceptance. No remote recipient service, retry, provider key or school authority is introduced. Real local capture/readback/exact-message cleanup and offline refusal tests verify this transport separately from recipient claim or production SMTP.

`identity/identity.service.ts` resolves verified sessions/current stored memberships. `identity/supabase-auth.ts` verifies tokens with Auth. `database/database.ts` supplies bounded pools and actor/school transaction context. Platform code depends on domain/contracts/config public packages, never application domain modules. Tests live in apps/api/test/unit and integration.

`AccountIdentityService` and `createAccountVerifier` supply a purpose-only account identity before school membership exists. The account result retains the current Auth server's subject, session, email and email confirmation time; JWT or editable metadata cannot supply email authority. Current session confirmation remains required, and no school, role, entitlement or membership is returned or looked up. The ordinary `IdentityService.resolve` and `createUserVerifier` retain their existing school contract. The unit-only account/identity tests use controlled Auth responses; this boundary has no public route, invitation delivery, recovery callback or admission command yet and does not establish completed onboarding.

`identity/provisioning.ts` owns a narrow server-only Supabase Auth adapter: create one exact server-assigned unconfirmed identity, reconcile that identity by ID, and generate an invite/recovery link for a fixed approved target/redirect. Caller-owned private approval and durable attempt/lease state must authorize each operation; provider identity is never school membership or proof of recipient control. Unknown create outcomes reconcile without another create, and uncertain links are never regenerated automatically. Links and OTP/redemption material do not enter its minimized receipts; an explicit transient secret sink consumes only a validated link. `GENERATED` means link generation and sink return, not delivered mail or accepted admission. No email lookup, user enumeration, deletion, metadata/role grant or provider retry exists. Offline injected-port and SDK/fetch cases plus an exclusive actual local Auth create/reconcile/invite sequence verify this boundary. Exact admission/recovery paths are in the local Auth redirect allowlist. No configured application credential recipient, route, durable executor, SMTP delivery or completed onboarding exists yet.

Provider `deleted_at` and `banned_until` are optional SDK fields, normally omitted for active accounts; absent/null lifecycle fields do not themselves deny this narrow identity read. A supplied deletion marker, malformed ban or current ban denies reconciliation/link consumption. The separate anonymous flag still requires explicit `false`. Provisioning `emailConfirmed` is true for a valid provider confirmation time, false for explicit provider null, and null for an omitted timestamp. Confirming exact account identity does not establish email control; an approved invite may proceed with unknown confirmation, while recovery and the separate account-admission identity verifier require confirmed email. Creation timeouts and contradictory error-plus-user responses retain `OUTCOME_UNKNOWN`; an HTTP4xx status alone never proves no external identity effect.

The explicit API server configuration now exposes a dedicated disabled-by-default `authProvisioning` recipient. Only LOCAL_SYNTHETIC with exact approved Auth/project/web targets can return its dedicated key; Storage is not a fallback, and worker/default-all/browser recipients receive none. Configuration does not compose or invoke the adapter, authorize a school request, send mail or prove onboarding. Hosted and real delivery remain unavailable pending their reviewed gates.

`request-limits/request-limits.ts` applies fixed one-minute read/write and connection-address budgets before protected routes perform Auth/database work. It stores bounded hashes in process memory, ignores untrusted forwarding headers, and returns a sanitized 429 with Retry-After. It supplements domain-level community limits and current authorization. It is a single-process safeguard; shared production gateway limits require deployment policy.

Database actor transactions record only fixed outcome, elapsed time and pool waiting count. SQL strings, parameters, actor identifiers and database errors stay out of timing telemetry. Request telemetry records fixed route templates/status/correlation; worker telemetry records queue lag and delivery outcomes. These records support local investigation; production alert delivery remains a deployment concern.

`health/readiness.ts` shares one in-flight dependency probe and caches its sanitized result for two seconds. Public readiness uses a separate per-address budget; changing bearer/query values cannot bypass it. Liveness remains inexpensive. API production configuration checks only API-owned credential consumers, avoiding distribution of the worker password merely to pass startup validation.

`telemetry/browser-diagnostics.controller.ts` exposes current-session configuration and fixed-field QA observations. Identity and the private SQL source recheck current school access, latest analytics policy and explicit active all-synthetic school activation. A random version-four diagnostic identity is its exact retry key; one source/audit/outbox commit is idempotent. Six enum fields describe category, feature, status, timing, locale and viewport. Raw errors, URLs, content, request data and selected-child identifiers are rejected. Private source rows have forced RLS and function-only API grants; recording is bounded to20 observations per actor and500 per school per minute. Outbox acknowledgment validates the immutable source but is separate from destination delivery. Product sources11/39/42/81/82 and SQL/API deny tests govern this boundary.
