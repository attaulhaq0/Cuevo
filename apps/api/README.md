# Cuevo API

The sequential `improvement-api.test.ts` fixture observes only its known measurement request through a test-only Database decorator. It reuses fixed query-failure metadata from `scale-query-diagnostics.ts`, with measurement authorization/lock/native/projection phases, allowed SQLSTATE or null and bounded duration. Failure output contains no SQL, bindings, actor/source identities, body, key or driver message; success is silent and the original request assertion/error remains unchanged. Offline actual-controller probes verify native/projection failures and observer/scope behavior. The production Database, SQL statement limits, source/receipt authority and remote ingestion are unaffected; actual next-run phase evidence is still required before diagnosing the CI measurement timeout.

Operator-only live verification shares `test/integration/customer-live-allowance.ts` with the explicit transport smoke script. Strict ledger validation, an exclusive owned lock and synced atomic reservation preserve the local three-attempt allowance across cooperating writers; ordinary integration remains fixture-only. `test/unit/customer-live-allowance.test.ts` uses temporary files and injected failure paths without touching credentials, the real allowance or a provider. This test utility supplies no runtime domain or billing authority.

`test/integration/customer-scale-measurement.ts` owns the scale fixture's real collector and teardown accounting. Attempted collector invocations, returned responses and successfully asserted samples are distinct; failed responses do not satisfy the planned sample denominator. Setup/worker timing stays separate, and final VERIFIED receipts require current fixture capture and completed cleanup. Offline injected-request/clock tests cover failed last samples and artifact/cleanup sequencing; actual API scale still needs its own execution.

`src/main.ts` starts the process; `src/app.ts` composes Nest controllers and HTTP/security setup. Domain behavior belongs in `src/modules/<domain>` and identity/database infrastructure in `src/platform`. See root docs/codebase-map.md and docs/architecture/repository-layout.md.

`src/serverless.ts` exports the separate hosted Node HTTP entry. It shares one initialized `createApp` across concurrent/warm requests, retries failed bootstrap on a later request and returns only a sanitized uncached503 if initialization fails. The host's original request/response reaches the existing Fastify server directly; controller authorization, raw parsing/body limits, correlation, status/headers and private binary bytes retain their current owners. It opens no listener. `npm run build:api-vercel` produces an ignored prebuilt Vercel function with Node24, explicit `shouldAddHelpers: false`, pinned installed production dependencies and verified runtime packs. Local HTTP/packaging checks are preparation evidence; hosted Auth, grants, private downloads, gateway rate limits and complete source/CI release acceptance remain required.

The disposable serverless HTTP fixture forwards `Expect: 100-continue` to the same handler for its oversized request. It verifies the actual Fastify413 before sending the rejected upload, avoiding a Windows unread-upload socket-reset race. The permitted-continue case verifies exact upload bytes after application permission. Ordinary raw binary/encoded URL/status/headers, JSON, malformed body and unchanged one-megabyte limit assertions remain active; no production transport or upload limit is changed.

Domain owners: school, school-learning, curriculum, academic, learner-state, improvement, community, portfolio, development and assets. Each module README lists sources, entrypoints and checks. Run from the root: `npm run build -w @cuevo/api`, `npm run typecheck`, `npm run lint`, `npm run test:integration` after local bootstrap, and `npm run db:test`. Tests are under test/unit and test/integration. No raw SQL/credentials or authorizations belong in web code.

Independent customer acceptance cases use customer-test-context.ts for real Auth/controllers and an isolated synthetic tenant: customer-journeys-api covers twelve longitudinal patterns, customer-scale-api measures bounded pilot-volume reads, customer-concurrency-api uses real committed races with precise tenant cleanup, and customer-observation-performance-api isolates the1002-source read budget. Mutation windows remain exclusive. Results and limits are recorded in docs/reports/customer-longitudinal-scale-verification.md; functional passes do not imply performance or production acceptance.

Scale setup and cases use the test-only CooperativeFixtureScope. A runner timeout does not cancel a handler or promise: guarded operations stop scheduling further work after the original budget/cancellation, and cleanup awaits the original body before owner metrics, rollback or the next case. Setup teardown waits for the normal API handler role reset before the fixture owner read; no API authorization role is bypassed. No early injection abort is treated as proof that PostgreSQL work stopped. Unit controlled promises verify in-flight settlement/role reset precede cleanup and a late response cannot schedule another query. Setup keeps all100 real academic API chains; per-phase/category timings and incomplete measurement counts remain evidence, with unchanged case/request budgets.

Test-only fixture-cleanup.ts attempts every owned cleanup step sequentially. Scale teardown closes its context even if a scope join, role reset or metric write fails; failed metrics remain failures and incomplete samples retain their measured denominator. Context creation covers connection, secret/identity preparation and transaction setup failures, while close attempts app/runtime pool shutdown, rollback, guarded committed-tenant cleanup, client release and owner pool shutdown independently. A single failure retains its original value; multiple failures retain the primary and ordered cleanup errors in AggregateError. Unit fixture-cleanup.test.ts verifies these error and ordering guarantees without opening a database or runtime.

The competing-worker fixture first calls `customer-worker-window.ts` within the exclusive local integration window. It verifies local target/role, stopped shared runtimes and entirely synthetic queue actors/school populations, then drains real pending source events through the restricted claim/process functions before asserting one test lease. It never marks arbitrary backlog complete through the owner connection. Nonclaimable active leases or invalid sources require review. Unit `customer-worker-window.test.ts` covers target refusal, unsafe population denial, exact source/lease processing and unresolved leases.
