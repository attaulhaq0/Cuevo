# Authentication presentation

Owns SignIn and AccessState components, exported through ui.tsx. Shared/session owns Auth client, current membership and provider state; shared/i18n owns common locale; shared/components owns branding/language controls. Auth presentation never depends on shell composition. Product source IDs 39, 62 and 63.

Authentication/client/membership unit cases live in shared/session/test, where their implementation is owned. Browser proof: tests/e2e/foundation.spec.ts. Keep denied, unavailable, expired and unknown states distinct; never accept a client-selected role as authorization or expose server credentials.

The founder-approved 1536x1024 auth concept supplies the current target: a full-bleed desktop split of 62.5% pale blue illustration and 37.5% white form, with large navy copy, four horizontal learning stages and a waving fox in its navy outfit with glasses and tablet. The official Cuevo logo sits inside the illustrated region and language controls inside the white region. The form is part of the white surface without a floating card. No company attribution text is visible on this auth surface; E Deviser remains the company and Cuevo the product. The earlier inspiration screenshot and desk fox are superseded for this feature.

On 1 October 2026 the founder selected mobile concept A, the compact welcome with the form first, preserved in ignored `.local/design-concepts/auth-mobile/compact.png` (1024x1536; SHA-256 `cd39280b557dcfc9b41ebbe2af9aca22265dc2df81835c6846f5502acc796dad`). Its mobile composition places brand and language controls on one compact row, then one visible Welcome h1 and school-account guidance beside a small version of the same waving fox. Mobile auth deliberately omits the learning diagram, role tray and duplicate desktop introduction, so the real form follows immediately. It adapts the approved desktop identity rather than introducing another authentication method or character asset.

`styles.css` owns the responsive composition; `messages.ts` owns English/Arabic story/help/privacy copy and `components/learning-loop.tsx` owns the stage/role labels and controlled UI icons. Independent generated background and alpha-preserving fox assets live in `assets`; their exact provenance and hashes are maintained in the [media README](assets/README.md) and [asset decision](../../../../docs/decisions/2026-10-01-auth-presentation-assets.md). The approved screenshot is not shipped as a functioning form. Shared `Brand` renders the separately supplied official Cuevo mark.

The sole authentication method remains the existing school-issued email/password sign-in with verified API membership. Account help, password visibility, language choice and privacy/device disclosure are real controls. Registration, password-reset delivery, magic links, persistent sessions, cookie consent and client-selected roles are not implied by visual approval. Form/help/error/privacy content must remain reachable in normal document flow under Arabic, enlarged text and short/mobile viewports; artwork must not cover it.

`tests/e2e/auth-reference.spec.ts` covers independent unauthenticated presentation, real keyboard interactions, EN/AR responsive/reflow/axe, source image decoding and mocked credential/service errors. `tests/e2e/auth-layout.spec.ts` covers geometry, enlarged text, reflow and native Chromium tab zoom in a disposable profile; viewport reflow and native zoom are distinct evidence. Test presence or asset decoding does not establish fidelity: compare the final concept and rendered page at the same viewport/state and record actual results. These presentation cases do not prove real Supabase/role authentication; retain the existing foundation/API/deny journeys for that. The current real multi-school error is classified as a specific recovery state without creating an unsupported school selector. Support IDs appear inside deliberate disclosures.

Current visual/test acceptance and the distinction between independent preview, mocked errors and real protected authentication are recorded in the [auth QA report](../../../../docs/reports/2026-10-01-auth-design-qa.md). Desktop and mobile visual approvals do not accept the wider role workspaces.
