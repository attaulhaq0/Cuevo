## Chosen execution boundary

Use a bounded School-owned API executor backed by the existing transactional outbox. An administrator explicitly approves one exact name, email and role. The domain command commits its immutable request, revision, canonical audit, original-key receipt and `school.account.provisioning_requested` event together. The API executor claims only that exact event after commit and reserves each external-effect attempt durably before calling the platform adapter. It runs no timer, global account scan or alternate task queue. The ordinary worker retains deterministic domain processing and never receives an Auth admin credential.

The reviewed event-owner classifier is one private immutable function, `internal.outbox_event_owner(text)`. Exact `school.account.provisioning_requested` and `school.account.recovery_requested` events belong to `SCHOOL_ACCOUNT_AUTH`; all other non-null event types retain `WORKER` behavior, including review of unknown legacy types. Metadata cannot choose ownership. NULL is not a worker-owned event. Apply the classifier to worker claim/exhaustion, complete/fail, processing and due/health predicates. Preserve the independent PostHog due-work branch and its existing allowlist. The reserved Auth events never enter analytics automatically.

The existing outbox remains the sole task ledger. Provider identity, link generation, SMTP acceptance, recipient claim and domain source acknowledgment are distinct receipts. An Auth event completes only when its exact executor has a confirmed delivery receipt or an explicit terminal revoked/review outcome; completion must retain the truthful final outcome. A terminal source acknowledgment cannot imply delivered mail or school membership. General worker recovery must never retry Auth create/link/send or turn a pending Auth event into an idle-loop wake. Strict fixture/global-queue preflights must expose or refuse unfinished Auth work rather than silently discard it.

## Credential and local delivery boundary

`CUEVO_AUTH_PROVISIONING_MODE=LOCAL_SYNTHETIC` requires the exact local Cuevo Auth URL/project and web origin, matching ordinary API configuration. `CUEVO_AUTH_PROVISIONING_KEY` is an explicit API/operator recipient, disabled by default. Web, general worker and default aggregate configuration receive no provisioning secret. Existing Storage credentials never supply a fallback. Provider keys remain broad provider capabilities; exact trusted SQL source and the reviewed adapter enforce the operation's purpose and target.

This implementation admits only local synthetic SMTP capture at Cuevo's existing local service. It never sends mail to a remote SMTP service, invokes live models, enables public signup or activates hosted/real-school admission. Production delivery, regional/privacy policy and initial real school/operator approval remain separate documented gates. No dependency or service replaces the current modular monolith.

## Request, lease and secret handling

Private request/revision/effect/token/claim records have explicit FORCE RLS, no raw application or Data API grants, bounded owner functions and immutable history. The approved source pins school, approving actor, name, normalized exact recipient email, role, expected provider UUID, expiry and revision. Claimants cannot choose school, role, entitlement, child or Auth metadata. Relationships are configured afterward by the real administrator through existing commands.

Lock order is school-access mutation advisory lock, administrator membership protection where relevant, request/current revision, exact outbox event, step/token, exact membership/person, then original command receipt. Provider and SMTP calls occur outside short row-lock transactions. A60-second durable lease covers the bounded execution; each network operation has a5-second timeout and no automatic retry. An expired reserved external-effect step becomes `OUTCOME_UNKNOWN`. Never release a lease while an uncancelled external callback can still act.

Supabase lacks an exact-email lookup/idempotent admin mutation surface in the installed SDK. Allocate one exact provider UUID and reconcile it through supported `getUserById`; do not search or attach arbitrary email matches. An unknown create can reconcile that UUID but cannot create again. Conflicting/existing-email admission requires explicit reviewed current-identity proof; it never reactivates revoked membership or alters an existing role. Unknown link generation or send cannot automatically repeat. Confirmed steps can be reused without repeating their effects.

Generate an independent256-bit application admission secret. Persist only its SHA256 digest and purpose/revision/expiry, with single consumption. Supabase `hashed_token` is a redemption credential, not a digest safe for storage. Provider action links, OTP, tokens, application secrets and email content never enter SQL/outbox/audit/logs/analytics or reports. The transient link sink builds the deliberate account continuation; the page removes sensitive URL fragments before ordinary UI/telemetry and does nothing on GET. Explicit Continue verifies provider control and sends the claim through a current verified account session. Email delivery does not itself establish school authority.

## Claim and operator authority

Recipient claim uses an actor-only API transaction and an exact session GUC. A narrow private owner function independently checks verified actor, current `auth.sessions` user/expiry, exact approved `auth.users` UUID/email, confirmed email, explicit nonanonymous state, deletion/ban, current request/revision/approval/expiry/token and the approving administrator's current authority. It derives school from the private request, repeats applicable synthetic admission inside that boundary, and serializes before inserting the approved active membership/person. Never fabricate a pending member to call ordinary helpers.

Consume the token, insert membership/person, preserve access-history triggers, and append normal audit/outbox/idempotent claim receipt atomically. Original-key replay repeats current source/member authority; revoked access cannot resurrect itself. A conflicting existing membership fails closed unless this is the exact previously completed claim. Repeated requests and concurrent claims require deterministic conflict/receipt behavior.

Initial school/first administrator admission is a separate restricted operator runner with exact approved source and private pre-school provenance. Ordinary API receives neither generic tenant creation nor owner credentials. After the first real membership exists, normal school audit/outbox can become valid atomically. Synthetic bootstrap remains a test-environment restorer and is never presented as onboarding.
