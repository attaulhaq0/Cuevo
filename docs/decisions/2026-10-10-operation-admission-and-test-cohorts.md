# Operation admission reuse and complete continuation test cohorts

Status: implementation and verification in progress, 10 October 2026. Protected integration, whole-CI timing and hosted/customer acceptance remain separate.

## Scope of the simplification

The goal is to remove unnecessary repeated execution and make the release understandable and resumable. It does not require every file or data input to be read only once. Current approval, target, history, private receipts, lease, source and executable-file checks still run at their required boundaries because those facts can change.

The proposed source-only preparation token and arbitrary historical-data lifecycle were deferred after review. Their focused tests reduced SQL payload acquisitions from three to one, but did not demonstrate faster preparation; the additional lifecycle and physical scans are not required by the verified current migration-recovery route. The active candidate keeps the smaller plan-bound source owner and planner-to-workdir handoff. Repeated source reads outside that owner remain measurable optimization opportunities rather than new release requirements. The draft and its evidence are preserved in ignored local recovery material.

The source-owner changes in schema execution, receipt persistence, Auth, population and provider deployment reuse immutable inputs within an existing operation. They preserve current state and authority checks, exact original effect identities and creator-owned cleanup. Their local tests and reviews do not establish hosted installation, complete candidate CI or customer acceptance. The full set of tracked audit obligations includes optional performance work, customer launch requirements and future lifecycle capabilities; it is not a checklist that must all be completed before the first synthetic staging deployment.

## Release operation lifetime

Preparation acquires original canonical source/database/security archives once and retains their guards. Its final boundary rereads original metadata, current controls, expiry and physical source. Completed recovery verifies its original archive and historical migration bytes once; final preparation refreshes official metadata or the exact current private Vault record. Mutable authority is never cached as permission.

Provider preparation/deployment, API origin observation/binding, publisher-step observers, runtime sessions, handover, public settings and exports reuse the existing opaque `NativeBackendAdmissionHandle` inside one operation. Current source/package/run/attempt/effect scope remains exact. Every original authority boundary still invokes the current reader. A typed borrowed handle stays outside serialized input and with its owner; null, forged, foreign, overlapping, failed or disposed handles refuse. The creating owner disposes after native/provider/session/output cleanup. Different workflow processes and effect scopes retain separate owners.

Physical SQL, CLI, artifact and private-record checks remain where mutable bytes are consumed. No generic cache, new approval capability or relaxed freshness is introduced. Uncertain outcomes cannot authorize another upload. Canonical migration planning verifies original Git source/tree/ancestry and complete historical inventory before allowing a formerly complete schema boundary after an append. A schema-only historical prefix cannot become populated complete-release evidence; supplied planning remains conservative.

## Continuation fixture scheduling

The continuation fixture uses global clocks, hooks, transport state and leases, so cases remain serial inside a process. The existing source-contract producer schedules five fixed title groups over the original file in separate Node processes and temporary directories. Each scenario keeps its existing repository/lease cleanup. Other files execute once in the ordinary batch. The default local complete-file command remains unchanged.

`source-test-cohorts.ts` owns the finite 25-parent/3-child inventory, five exact escaped patterns, report validation and logical file union. `ci-partitions.json` binds its policy digest. Actual physical declaration discovery precedes dispatch; added, removed, aliased, dynamic, skipped, TODO or unassigned declarations refuse. Children remain with their parent.

Node filtering can omit cases with zero reported skips. A passing filtered report therefore cannot prove full coverage. Acceptance requires all five original process receipts, exact title/parent/definition identities, source/file/toolchain/run/attempt binding, original exit/cleanup and containment within the partition's actual clocks. All 28 cases must appear once. Missing, extra, duplicated, failed, cancelled or substituted evidence refuses. Logical file duration is the observed first-to-last wall span, not summed case time.

Existing source partition and required aggregate names/artifact identities remain. Current policy requires cohort evidence for the selected file; other files cannot carry it. Historical consumption derives policy and inventory from exact original Git bytes and retains strict source/decoder binding. Old receipts without this policy do not acquire current cohort authority. Scratch removal follows confirmed shutdown; unconfirmed cleanup stays review. Safe reports exclude raw private errors and credentials.
