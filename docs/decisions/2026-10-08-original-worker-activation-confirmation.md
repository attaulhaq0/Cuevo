# Original worker activation confirmation ownership

Status: bounded initial-route direction approved on 8 October 2026; controlled source verification is in progress. Actual hosted execution and fresh pending-package recovery remain separate gates.

The initial activation wrote successful local result/cleanup before an unowned second pg Client confirmed private active state. The supported Node 24 reproduction demonstrated uncaught idle error handling and stale terminal files after final confirmation failure. One additional listener alone would not fix the receipt/unknown-commit boundary.

`scripts/verification/backend-hosted-activation-confirmation.ts` owns that final native session, with error/end listeners, live TLS/identity checks, the original advisory lease, fixed GET provider and private native observations, independent original key evidence and one CONFIGURED → CONFIRMED save/CAS/readback. Exact already-CONFIRMED readback performs no save. COMMIT uncertainty stays unknown until a separately admitted native observation. It never creates a key, deploys, replays a source/wake or pauses healthy active dispatch.

The existing pure owner `scripts/database/hosted-active-runtime-state.ts` adds a confirmation-candidate validator bound to immutable original identity, key/configuration digests, complete activation and cleanup. Ordinary installed-runtime metadata and private-configuration readers remain CONFIRMED only. No migration or alternate receipt ledger is introduced.

Initial activation retains original execution evidence as `worker-activation-execution-result.json` and `worker-activation-execution-cleanup.json`, preserving clocks/hashes in private CONFIGURED/CONFIRMED state. The existing final result/cleanup paths are published after confirmation cleanup settles. Current cleanup aggregates original and confirmation lease/session facts; failed overall results cannot satisfy strict release consumers. Original actual execution failures retain exact owned dispatch/Cron cleanup, while late observation/publication/cleanup review preserves healthy work and reports unknown/review truthfully.

A final file write may produce matching success bytes before its fsync/close fails. Local files therefore cannot independently authorize direct complete-backend consumers. `readBackendActivationExecutionAdmission` requires the exact current official schema job's completed successful signed-execution step under fresh source/run/attempt/founder admission; a still-running parent job is permitted. Direct fault/API/handover owners require this provenance beside their existing native and result/cleanup gates. The backend runner throws on any activation review, making the official step fail. Installed-runtime keeps its separate current native CONFIRMED proof. No recursively uncertain completion-marker file is introduced.

Direct consumers also invoke the same confirmation protocol with strict `observationOnly:true`, which refuses CONFIGURED before any save and requires exact original CONFIRMED execution/cleanup/key and current private/provider observations. The fault owner performs this before opening its own operation lease. API and handover use their protected operator inputs. The observation returns no new installed-runtime authority and cannot create an earned or provider effect.

Controlled tests exercise the exported native owner using the installed pg Client/EventEmitter error path and independent pending/save/commit/readback state. They cover lost acknowledgement, later exact observation, original key changes, provider reuse, private/source/control denial, unlock/end and journal failure. Source tests establish only the exercised behavior.
