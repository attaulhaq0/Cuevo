# Local synthetic quick login

The founder requested quick login for faster team testing on 4 October. This adds a bounded local review convenience, not a new account, role-switching authority or authentication provider.

Auth owns one server-only public `api.ts` surface and `server/quick-login.ts`; Next's exact `app/api/testing/quick-login/route.ts` only composes that owner. Browser Auth components never import the server surface, local filesystem or credentials. The architecture guard permits filesystem/path/URL modules only in this exact owner and rejects browser imports into it, unrelated server folders, runtime database clients and server configuration packages. Next's `server-only` marker provides an additional build boundary.

Availability requires an explicit server-only opt-in, exact local review origin and matching local synthetic Auth endpoint, with no hosted deployment. The source-locked 133-person synthetic manifest and ignored current account file must match exact actor, email and role before use. The request never supplies an email/password, actor ID or arbitrary role value. The disabled path supplies no configuration or credentials; POST requires the exact origin and current allowlisted role. Credentials are read only by the server and never serialized into HTML, public config, browser bundles or logs.

The local issuer also verifies the real managed standalone process entry and its parsed standalone configuration against the same repository root before reading private credentials. The generated entry actually consumes the explicit loopback HOSTNAME. Bare Next CLI startup remains unavailable even if the environment declares a local hostname; a caller-supplied Host or forwarded header alone cannot prove transport ownership. Request bodies are limited to256bytes and one second, and the client aborts requests on timeout/unmount before stale session restoration.

The server performs a normal password sign-in against the verified local Auth endpoint using its publishable key. The selected account's actual authenticated identity must match the source. The response contains the limited session tokens needed by the existing browser Auth client; it does not grant membership or hide permission checks. Shared session restoration uses the same client and current membership verification as ordinary sign-in. Current tenant, entitlement, role, relationship, object, source and publication checks stay authoritative.

The approved customer authentication composition remains one deterministic form. A compact testing control is discovered after mount only in the enabled review runtime. One pending state coordinates ordinary sign-in and quick login, with localized failure/retry and normal sign-out. Browser/device layout and source/credential scopes do not establish customer readiness.

Tests must verify default-off, hosted/remote/wrong-origin refusal, malformed/duplicate/non-synthetic account sources, real Auth identity mismatch, sanitized errors, no password output, pending/retry/EN/AR behavior and all five real local memberships. Production release environment allowlists remain unchanged. Removing the opt-in disables quick login without changing authentication or existing accounts.
