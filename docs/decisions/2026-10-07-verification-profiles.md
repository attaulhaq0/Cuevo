# Verification profiles and release evidence

Status: founder-authorized architecture on 7 October 2026; source implementation and verification are in progress, with integration and managed execution unverified. The founder expanded the task from the first synthetic provisioning lane to correcting CI architecture first. This decision supersedes the earlier assumption that every PR and main push must repeat the entire customer regression and packaging sequence. It preserves required protected PR/main checks, immutable source evidence, complete affected security/domain suites and the full customer-release gate.

The previous `Cuevo verification` workflow repeated stateless checks inside a long technical run, replayed local fixtures, built unrelated runtime outputs and executed the complete browser/outage/restore matrix before hosted schema work. Repeating that bundle for each browser repair gave slow feedback while Supabase remained unprovisioned. The accepted architecture gives routine changes connected verification, runs exhaustive regression separately, and keeps installed-provider receipts distinct from both kinds of local evidence.

## Four verification boundaries

| Boundary | Trigger and scope | Evidence and permitted use |
|---|---|---|
| Routine stateless/security | Every PR, main push and explicit routine dispatch; structure/docs, lint/types/unit/contracts, dependency checks, processed CodeQL and source/history secret scan | Exact source and successful required jobs; no runtime or hosted claim |
| Runtime verification by event/impact | PR changes to existing mapped feature UI may use routine; public/security/shared/server/new/unknown changes use broader affected runtime. Every integrated main uses full SQL/all API/signed Edge/artifact privacy with core and admitted mapped-owner Chromium journeys | Distinct `ROUTINE`, `FULL_RUNTIME` or `MAIN_STAGING` evidence only when its complete selected inventory and source freeze pass; none is full customer acceptance |
| Full regression/customer candidate | Separate main-only full-regression workflow; daily at 03:17 Riyadh or manual `regression`/`customer-candidate` purpose | Complete technical/browser compatibility/account/outage/restore matrix and selected web/Vercel API/Edge artifacts; scheduled/general regression provides coverage, while only exact verified manual `customer-candidate` authority is eligible for production admission |
| Hosted operation and release admission | Explicit existing backend and manual-only web workflow after current source, provider, artifact and founder gates | Actual installed milestone receipts; production retains canonical main/backend CI identity A plus separate exact customer-candidate full proof B, with A and B distinct |

The independent [initial synthetic schema/account lane](2026-10-07-focused-synthetic-provisioning.md) remains within the fourth boundary. It can use its exact focused schema/Auth verification proof and cannot deploy providers or issue a complete frontend certificate. Routine and focused success do not replace actual hosted SQL, Auth, private Storage/Realtime, worker execution/recovery or customer acceptance.

## Workflow and profile ownership

`.github/workflows/ci.yml` keeps the name `Cuevo verification` and existing required job identities: `fast-checks`, `technical-mvp`, `codeql`, `secret-scan`, PR-only `dependency-review` and `required`. `stateless-checks.ts` derives all original nonruntime verification/fixture groups from the shared inventory and runs them once in `fast-checks`; lint/types and unit/web-unit remain in that same fast job once. `runtime-backend` and `runtime-browser` invoke `technical-exit.ts --profile=ci --lane=backend|browser` on separate Ubuntu runners, each with its own Docker stack, bootstrap, local credentials and production build. `technical-mvp` is the aggregate and consumes only the two fixed same-run/attempt lane JSON artifacts. A PR uses focused routine or broader affected runtime scope; every integrated main uses `main-staging`. It does not rerun stateless sibling checks. The required aggregate refuses failed, cancelled, skipped or missing mandatory work; dependency review remains explicitly PR-only.

`scripts/verification/verification-workflows.ts` owns exact routine/full workflow contracts and `fullRegressionJobPolicy`. `verification-profiles.ts` owns parsing, selected steps, critical integration/browser files, change admission and strict result validation; `playwright.critical.config.ts` supplies the existing production runtime with Chromium. Profiles compose existing owners. Default local `verify:technical` remains complete. `ROUTINE_VERIFIED`, `FULL_RUNTIME_VERIFIED` and `MAIN_STAGING_VERIFIED` carry their exact ordered required rows and source freeze; strict row schemas refuse extra diagnostic/private fields and none substitutes for full `VERIFIED` customer evidence.

The selected deployment route builds production web, the existing Vercel API artifact and Supabase Edge artifact and verifies artifact/browser privacy. Legacy Docker release-image builds are removed from this route; any optional alternative runtime needs its own separately admitted checks. Routine PR runtime uses full SQL,13critical API owners, real signed Edge execution and core five-role bilingual/mobile Chromium cases plus admitted owner journeys. Every integrated main uses full SQL/RLS/grants, all API integration, real signed Edge execution, selected artifact privacy and core Chromium plus admitted mapped-owner journeys, then guarded restoration/source freeze. Main staging does not run the complete700-case customer matrix. Firefox/WebKit and full English/Arabic/mobile/keyboard/accessibility, outage and restore journeys remain the full boundary.

High-impact changes run their complete affected suites in the routine workflow:

- Auth/account/session, access/relationship/entitlement and relevant contract changes require complete affected Auth/admission/recovery/revocation and authorization tests.
- Every migration, SQL/RLS/grant, seed or database-operator change requires complete SQL/RLS/grant/provider, immutable replay and affected migration/Auth suites. The initial routine profile retains the full database suite even for other changes until measured evidence supports a separately reviewed reduction.
- Worker/outbox/wake/event/lease/scheduling/configuration changes require complete affected worker, source, retry/lease/recovery and Node/Edge parity suites. A browser result cannot establish deterministic processing.
- CI/workflow/release/admission/test-runner/runtime/bootstrap/lockfile changes require complete affected orchestration/security/credential/refusal contracts and the runtime suites whose execution they change.

The reviewed PR policy admits modifications/deletions of existing files in explicitly mapped web feature UI owners, including TS/TSX, CSS and Markdown, with core critical journeys plus the union of affected owner journeys. Public model/API/copy/UI surfaces, server/session/authorization/policy paths, Auth, shared code, routes, contracts, SQL, worker, CI, runtime/configuration, changed import/export/dynamic dependency boundaries or server directives, new source files, unknown owners/extensions, empty changes or unavailable policy choose broader `full-runtime`. The immutable baseline selector must match current bytes before narrowing. Every integrated main chooses `main-staging`, with all API/SQL/signed Edge and core plus affected Chromium owners. Unknown main changes retain all mapped owners. This mapping is conservative ownership coverage, not a transitive-risk proof or a promised completion time.

## Full regression and customer-candidate authority

`.github/workflows/full-regression.yml`, named `Cuevo full regression`, is separate from routine verification. Its jobs are `technical-mvp`, `codeql-evidence`, `secret-scan` and `required`. It runs the complete technical/browser compatibility/account/restoration/outage/recovery matrix with selected production web/Vercel API/Edge artifacts. It does not rebuild legacy Docker release images for this route. `codeql-evidence` consumes exact-main completed CodeQL proof from canonical CI without waiting for unrelated main-staging jobs; source/workflow/processed-analysis identity still must match. A failed or missing CodeQL/security/technical job blocks the full aggregate.

The daily UTC slot is `00:17`, equivalent to **03:17 Asia/Riyadh**. Manual `regression` and `customer-candidate` purposes remain distinct; a scheduled event can never choose customer-candidate release authority. `full-verification-evidence.ts` produces one safe summary artifact with exact source/run/attempt/purpose and complete selected result identity. It contains no account credentials, raw content, private logs or traces.

`release.yml` is manual-only. Its `ci_run_id` is A: the successful canonical current-main `Cuevo verification` identity already used by backend/dependency evidence. Production additionally requires `full_verification_run_id` B: a separate successful manual customer-candidate full workflow for the same exact source, with B≠A. Staging forbids the full-candidate input. `currentCi` verifies A before reading B's complete official run/attempt/job/safe-summary proof. Passing A never becomes full customer evidence, and B never replaces the original backend identity.

The production review package binds `fullVerification: { runId, runAttempt, sourceSha, summarySha256, jobsSha256 }`; it is mandatory for production and absent for staging. Admission repeats exact current source/run/attempt/digests before consumers. Scheduled/general regression, another attempt, missing/tampered summary, PR merge-tree or old source is refused. Current main, signed commit, protected PR/status rules, independent review, founder artifact approval, actual backend/provider dependencies and final known-artifact promotion approval remain required. Staging uses successful current-main `MAIN_STAGING` authority and actual source/package/provider receipts within its scope.

The earlier automatic production handoff after canonical main-push verification is superseded by explicit manual dispatch with distinct A/B proof and exact founder approval. Neither routine nor full workflow completion automatically dispatches production. Failure, cancellation, skipped required work, missing receipt, changed source or incomplete official pagination fails closed. Source contracts and review do not establish an actual hosted/prod release.

## Installed operation continuation

The approved backend workflow has three explicit scopes. `schema-and-accounts` admits installation only. `complete-backend` may consume confirmed installed schema/population and perform the existing provider/private/activation/recovery/handover sequence. `installed-runtime` is restricted to the same source as the already confirmed active runtime and obtains fresh verification/recovery/restore/handover authority; it cannot apply migrations, seed accounts, deploy providers or create another activation key.

Original population source and completed migration source are independent. The seed commits an original private command/audit receipt in its transaction. `hosted-installed-state.ts` defines that immutable population receipt, the latest completed migration inventory and original confirmed schema-stage progress. The native database writes the fixed private Vault stage record only after an original COMMITTED stage. Re-admission independently verifies historical Git bytes and every original remote committed stage; SQL history alone cannot clear an uncertain journal. Installed stages with no pending SQL emit revalidation evidence without a replacement COMMITTED command. Pending migrations remain append-only.

`backend-runtime-resume.ts` retains original activation identity, signing material and runtime configuration privately in Vault. Public preparation reads only the strict confirmed metadata projection, including the original run/attempt/package and activation receipt digest. A new approved same-source operation checks actual provider artifact/operation identity, private configuration, current roles/memberships, exact fictional accounts, signed delivery controls and owned recovery Cron. It preserves original activation receipts and creates separate current verification evidence. The deployment receipt is labeled `DEPLOYED_ACTIVE_REVALIDATED` with no deployment mutation; actual API health and worker denials remain separate fresh hosted checks.

Credential recovery uses the same encrypted original runtime record, current restricted role memberships and real TLS/password logins. CI artifacts never contain passwords, wake keys or runtime configuration. The backend/web handover binds native history, private inventory, original account evidence, current private probes, original activation plus current revalidation, current fault/restore proof and the approved public frontend settings. An approval expiry limits new effects; it does not erase original completed records or authorize restamping their clocks.

Canonical CI identity A now also binds `canonicalRuntimeVerification: {runAttempt,jobsSha256}` into backend and web review packages. Its native reader requires all mandatory main jobs and the exact backend/browser/technical aggregate authored steps. The optional PR-only dependency job may be absent or explicitly skipped on main. Missing, changed or differently attempted evidence refuses admission, including across separate review and deployment jobs. Customer-candidate B remains a separate exact full source proof.

Confirmed continuation is not universal automatic recovery. Unconfirmed migration/provider intents, an activation configured before terminal cleanup, and a later source over an active runtime need original-effect reconciliation or a separately reviewed rollout transition. No retry may create a replacement key or silently clear that history. Implementation, managed CI, installed provider state and complete hosted customer acceptance remain distinct.
