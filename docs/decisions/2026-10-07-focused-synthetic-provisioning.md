# Focused synthetic schema and account provisioning

Status: founder-authorized scope on 7 October 2026; implementation and verification are in progress. This milestone prepares a bounded initial Supabase provisioning route. No hosted migration, account creation, API/worker deployment or customer acceptance is established by this decision or its local tests.

The founder requested an urgent way out of the repeated full customer-verification loop so the existing hosted Cuevo project can receive its source-backed schema and fictional accounts. The accepted change separates that initial infrastructure milestone from the complete backend and customer-release gate. The later same-day [verification profiles decision](2026-10-07-verification-profiles.md) expands the work to CI architecture first: routine required verification, separate exhaustive daily/customer regression and exact customer-candidate production authority. This focused schema/Auth lane remains independent within that architecture. It keeps protected, signed `main`, PR integration, independent source/QA review and exact founder staging-package approval. It introduces no application branch, migration rewrite, automatic retry, new credential recipient or production bypass.

## Verification and evidence ownership

`.github/workflows/staging-verification.yml` is a main-only, secret-free verification workflow triggered by a push to `main` or explicit manual dispatch. Its `staging-checks`, `staging-database`, `codeql` and `secret-scan` jobs must all pass before `staging-required` passes. Existing structural, documentation, lint, type, unit, release-contract, migration/Auth-contract and dependency-security checks remain. A disposable owned local Supabase stack runs the guarded clean synthetic bootstrap, complete SQL/RLS/grant/provider fixtures and database advisors. Every job confirms the frozen authored source. CodeQL checks the current processed findings, and the secret scanner checks source/history. No hosted database, Storage, Auth provisioning, Vercel or email credential is supplied to this workflow; CI does not enable analytics ingestion.

The focused scope omits the complete browser matrix, outage/recovery journey and selected production web/Vercel API/Edge artifact verification. Those remain with the stage-appropriate connected/full boundaries. Legacy Docker release-image builds are removed from the selected route in the profiles ADR. Focused success establishes preparation for `SCHEMA_AND_SYNTHETIC_AUTH` only; local database fixtures do not establish installed hosted tables or working team access.

`scripts/verification/staging-verification.ts` owns the exact workflow contract and `validateBackendVerificationRun`. Backend preparation may accept successful current-main `Cuevo verification` staging authority, whose integrated-main runtime is `MAIN_STAGING`, or the exact focused workflow for the same main SHA/repository, within their admitted scopes. A PR merge-tree, feature-branch, failed, incomplete, foreign or differently named workflow is refused. Production full customer evidence is a separate identity/authority in the linked ADR; PR routine, scheduled regression and focused success remain insufficient.

`staging-verification-jobs.ts` reads the official focused run attempt and complete bounded job pages. It requires the exact successful job set, source/run/attempt identity, ordered authored steps and successful required steps; malformed, skipped, duplicate, incomplete or changed proof fails closed. It derives `jobsSha256` from that normalized official evidence. Focused backend intent and expected authority both retain `stagingVerification: { scope: 'SCHEMA_AND_SYNTHETIC_AUTH', runAttempt, jobsSha256 }`. Preparation and every native admission re-read the current run and jobs and require the same digest. A caller-supplied success boolean or workflow summary is insufficient.

## Initial hosted milestone

The existing manual `backend-release.yml` gains `scope`, defaulting to `schema-and-accounts`, with `complete-backend` as the other choice. The schema/account scope runs the existing source/package preparation, exact founder admission, fixed private operator-bucket bootstrap, original cumulative migration stages, synthetic reference population and Auth provisioning owners. Existing provider target, selected session endpoint, verified TLS, current source/tree, immutable migration bytes/history, complete private journal inventory, lock, freshness and original-command checks still apply.

Focused evidence is refused by the backend runner before every mode except `approval`, `bootstrap-schema` and `provision`. YAML also skips later provider, private-flow, activation, recovery, restoration, API-origin and web-handover steps for `schema-and-accounts`. Choosing `complete-backend` cannot elevate focused proof. Complete provider deployment and frontend handover continue to require actual backend/provider evidence and the stage-appropriate verification authority in the linked profiles decision. Focused proof never supplies complete provider or production authority.

The result artifact retains only the existing allowlisted schema/provisioning status and original metadata journals. Generated account passwords, certificates, runtime configuration and provider keys remain private and excluded. An exact confirmed hosted schema receipt and confirmed original fictional-account receipt establish only those installed milestones. They never satisfy the complete backend dependency manifest, export a frontend release certificate, claim a working hosted app or close MVP Gate 5.

## Failure and continuation

An unknown migration commitment, schema/history mismatch, unresolved journal, uncertain account effect, missing source or changed approval stops the original operation at `REQUIRES_REVIEW`. Do not rerun with a new key/package, reset the project, erase a journal, recreate accounts or refresh a proof clock to manufacture success. Preserve the actual original intent/outcome and perform the existing read-only reconciliation.

The preparation/executor is initial-only: populated Auth/domain/history state is not admitted as an empty target. A successful schema/account milestone therefore does not authorize a fresh initial `complete-backend` dispatch against the now-populated project. Later deployment must admit its actual retained schema/population/account receipts through the existing owners and current complete release requirements. Any missing continuation capability is explicit remaining work; this amendment does not silently relax population or recovery checks.

## Delivery milestones

1. Prepare, verify and review the focused lane; integrate its signed source through the existing protected PR/main process.
2. Observe the exact current target and run one original approved schema/account operation. Report actual migration history and fictional-account receipts separately.
3. Complete the source-backed populated-target continuation, full backend/provider checks and verified frontend transfer, then perform hosted customer testing.

At this source milestone, hosted SQL/Auth execution and all later provider milestones remain unverified. Workflow source, a passing focused run and a prepared package are three distinct facts; none substitutes for the hosted receipt.
