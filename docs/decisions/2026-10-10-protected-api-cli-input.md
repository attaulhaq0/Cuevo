# Protected input for the Vercel API CLI

Status: bounded implementation and verification in progress, 10 October 2026. Physical Linux execution, protected CI, hosted deployment and customer acceptance require separate evidence.

## Problem and scope

The previous API deployment path discovered a globally installed Vercel 62.1.0 entry and copied the admitted API prebuilt output before current admission. Its final hashes checked the observed entry and delivery, but neither the complete CLI dependency graph nor its Node toolchain had an enforced immutable execution boundary. Repeated full delivery traversal could also consume the short current-observation window. The approved deployment repair requires a complete protected input prepared before live admission, with unchanged freshness and original-effect recovery semantics.

This decision covers only the existing API preview CLI invocation. `backend-provider-deploy.ts` continues to own official/source/native admission, durable API deployment intent, inactive posture, original operation identity and uncertain-upload discovery/adoption. Domain, SQL, worker, web release and approval authority remain with their existing owners.

## Prepared-input owner

`scripts/verification/backend-provider-cli.ts` owns this provider-specific preparation and child lifecycle. The exact Vercel 62.1.0 manifest and dependency lock live under `scripts/verification/provider-cli`. Preparation reads those two immutable Git blobs from the current executor source, matches their physical bytes and rechecks that source and both inputs after installation. The executor source remains explicit and separate from a retained runtime artifact's source during rollback. Preparation uses the committed lock with `npm ci`, scripts disabled and optional packages omitted. It verifies the complete installed package/file/link graph, confined resolution and source inputs before snapshotting any execution bytes. A top-level version or entry hash alone is insufficient.

The source manifest admits only the reviewed exact twelve dependency overrides for this pinned CLI. Their current full graph receives the existing fixed dependency-security owner’s separate nested CLI audit, with optional packages omitted consistently. Earlier unmodified CLI graph receipts remain historical. Credential-free version/help, static configuration positive/invalid cases and exact prebuilt selection were tested for the reviewed graph; this does not establish a hosted deployment.

Graph capture checks each recursive directory before and after its children, including physical resolution, identity, mode, timestamps and the complete entry-name set. Each regular file is read through one `O_NOFOLLOW` descriptor, then compared with its original descriptor/leaf identity and full resolved path. This removes repeated ancestor traversal for every file without caching authority or accepting a writable host binding. The two source manifests retain the complete physical source checks. Parent replacement, link substitution and changes during an awaited read remain refusals.

Preparation failures retain only the fixed preparation phase, owned UUID and confirmed/unconfirmed cleanup in the existing failed provider result. The release runner saves that result before refusing completion. No token, stdout, raw container environment or private payload enters those diagnostics, and failed evidence cannot advance successful deployment or handover.

The owner snapshots the complete verified CLI graph and the existing verified API artifact into an offline-built private image on a pinned Node Linux base. It does not rebuild the API. The snapshot includes the exact prebuilt output and project linkage. Neither a mutable checkout/global install bind nor a same-writer permission bit establishes this boundary. The trusted Docker supervisor and pinned base supply the declared toolchain; the mechanism does not protect against an administrator controlling that supervisor.

The stopped owned container uses a nonroot read-only root, no inherited bind mounts or ambient module/preload configuration, and separate bounded writable scratch for the supported cache/config/tmp behavior. Node disables legacy global module search, the CLI entry is absolute, and its complete `node_modules` folder shape stays immutable. Delivery contains only prebuilt output and project JSON; the explicit global configuration is scratch JSON, native selection and updates are disabled, and no user JavaScript configuration is accepted. Scratch `noexec` alone does not stop Node imports. This controls the observed ambient resolution paths while the trusted pinned CLI retains its intended behavior. Exact image/input/source/artifact/project/target/operation, argv, environment and scratch bindings are verified before consumption. Private Vercel credentials are passed only to the exact stopped container through its private environment; they are excluded from public inputs, tar contexts, images, manifests and safe logs. The trusted supervisor can inspect that private environment, so it must never be printed as evidence.

Preparation returns no approval capability. After the existing owner renews current official/native facts, it synchronously consumes the original package/permit/posture limits immediately before starting the child. For this API launch, the owner captures the actual host clock immediately before its current official admission read and caps launch at that original clock plus thirty seconds. It combines that cap with the current native/posture deadline and absolute package expiry. The same absolute deadline is checked inside the child immediately before the pinned Node/Vercel execution; supervisor startup cannot extend it. The existing rollout owner exposes only its issued lease's actual current native deadline, with the original package expiry; reading it never refreshes facts or grants a launch. Exact prepared-input checks replace the former mutable launch traversal only after equivalent tampering, deadline and physical execution proof exists. The protected workflow retires the obsolete global Vercel installation step.

One attempt is terminal. Failed or cancelled work drains the owned child before cleanup, and unconfirmed image/container removal remains reviewable. Preparation, start, output loss or cleanup uncertainty never authorizes a second upload. Original deployment discovery/adoption stays in `backend-provider-deploy.ts` and uses the same original identity with zero new uploads. This is no shared runner, SQL port or second effect ledger.

## Discovery and verification

`backend-provider-cli.test.ts` is colocated with the owner and appears once in the `test:cicd` command, required `cicd-fixtures` inventory and `source-delivery` producer. Its measurement remains `durationMs: null` until a source-bound measurement exists. Existing complete discovery, same-source/run/attempt aggregation and required statuses remain intact.

Controlled transport fixtures exercise the actual owner’s graph, source/artifact/target binding, private credential exclusion, stopped-container checks, one attempt, expiry, cancellation and drained cleanup. Windows transport control does not prove physical read-only enforcement. The Linux test requires actual credential-free version/help execution on the pinned snapshot, attempted forbidden writes/import-path changes and writable-scratch behavior. Missing prerequisites or incomplete execution cannot become passing physical evidence or hosted acceptance.

Prior local Linux namespace/chroot probes ran the exact CLI version/help and real bundled prebuilt-file inspector against the existing API artifact. They demonstrated compatibility in that local layout and retained the complete selected file inventory. Their host paths were not a pinned Docker toolchain snapshot, and the input origins remained writable outside the namespace. The probe-specific native/update/cache controls and real inspector duration do not establish this owner’s physical execution, current admission-to-exec margin, provider upload or a pipeline timing target.

Acceptance still requires actual complete-inventory preparation/admission/supervisor-start/child-exec timing with unchanged deadline margins, tampering and delayed-start refusal, original loss/cancellation recovery, independent source review and required protected CI. A separately authorized exact synthetic preview upload and original provider readback establish the hosted milestone. Edge content, hosting capacity/configuration, five-role English/Arabic/mobile/private/recovery and customer approval remain separately scoped.
