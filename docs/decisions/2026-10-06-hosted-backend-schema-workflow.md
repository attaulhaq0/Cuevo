# Hosted backend schema workflow

The founder authorized completing the missing deployment runner using the existing Cuevo repository, Vercel web/API projects and Supabase Edge/Cron direction. This increment implements the first hosted execution phase: exact-source preparation, protected staging admission, fixed operator journal bucket bootstrap and the original cumulative migration stages. It does not deploy the API/web, seed accounts, activate the worker or certify a customer release.

`.github/workflows/backend-release.yml` runs only by explicit main-branch dispatch, with one serialized backend window. Its preparation job receives a repository-scoped Supabase Management token for fixed read-only metadata and `CUEVO_GITHUB_RELEASE_METADATA_TOKEN` for official read-only Actions/source/environment/branch-protection evidence. GitHub's ordinary Actions token does not offer the Administration read permission needed by the protection endpoints. The metadata credential requires only Cuevo repository access with Actions, Contents, Environments and Administration read; it is not a source-write or deployment credential. Actual endpoint access still requires verification. Preparation receives no database, Storage, Auth provisioning or Vercel credential. The existing source/package owners bind the current signed main source, successful main-push CI, assigned independent reviews, original migration bytes and generated API/Edge artifacts before writing the secret-free package.

The protected staging job downloads only the package from its own run and attempt. `scripts/verification/backend-release.ts` verifies the bundle digest and current source/run/attempt, then calls the existing official founder admission owner before receiving private operational inputs. The actual schema step rechecks admission, bootstraps only the fixed private operator bucket, and invokes `executeNativeHostedMigrations`. That native owner holds one actual PostgreSQL session lock across all four replay-derived stages and preserves each original durable intent, history and uncertain result. It uses the existing source, TLS, process, journal and provider adapters; no application-domain authority moves into the workflow.

The bundle has a separate bounded canonical execution envelope because the original 229 migration rows and cumulative stages exceed the smaller review-package limit. The shared encoder remains the owner. Review packages retain their original size and structure; the larger envelope does not relax founder approval or accept arbitrary executable inputs.

The repository secret `SUPABASE_ACCESS_TOKEN` serves preparation and fixed Management operations. Staging environment secrets `CUEVO_MIGRATION_DATABASE_PASSWORD`, `CUEVO_DATABASE_TLS_CA` and `CUEVO_RELEASE_JOURNAL_STORAGE_KEY` have separate native consumers. Credentials never enter the package, command arguments, browser configuration or public summary. The result artifact preserves sanitized schema/bucket outcomes and the native append-only metadata journals; certificates, process directories and private runtime inputs are excluded. Missing or uncertain native outcomes fail this phase; no automatic reset, migration reapply or cross-run journal adoption is added.

Current source tests establish preparation/credential/sequence refusal and native held-stage composition within their stated scope. Actual GitHub execution, hosted certificate/database connection, migration completion, original cross-run recovery, account/reference provisioning, API/Edge deployment, private-flow verification, worker activation, web deployment and five-role hosted acceptance remain required work. A passing schema phase must not satisfy the existing complete backend dependency manifest by itself.
