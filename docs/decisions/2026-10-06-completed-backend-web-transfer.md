# Completed backend handover to the existing web release

Status: bounded pipeline completion authorized by the founder's internal team MVP deployment request and accepted by root on 6 October 2026. Source implementation and controlled checks do not establish a successful hosted backend/web release.

The backend's mutation owner requires a live admitted run and an unexpired original package. The web release has its own `PREBUILD_RELEASE_ADMISSION` purpose and protected founder approval. Keeping the backend waiting for a second approval and build would couple its operational expiry to another runner. The backend instead exports one canonical `web-transfer.json` after the existing native handover, private recovery/restore cleanup and public web-settings proof. It then completes normally. The new read-only completed-run consumer does not relax or replace the live backend admission.

The transfer includes the original small public backend approval package, original admitted run/CI snapshot, strict version-two web dependency manifest, public-settings digest, fixed producer source hashes, required original native receipt hashes and original export/proof clocks. It excludes the execution bundle, runtime configuration, certificates, database/private-file archives, Auth accounts, keys and raw pupil/source content. Native receipt details stay in their existing restricted evidence artifact. The exporter rechecks the real native handover and exact evidence bytes before its exclusive synced file write; partial or conflicting output is retained for review.

The importer accepts only a trusted main manual staging web release. It reads the actual successful completed backend run/attempt and official artifact metadata, verifies the GitHub archive SHA-256 before decoding, then uses the ZIP reader already bundled in locked Playwright to require one bounded regular `web-transfer.json` entry. It never extracts or executes an artifact. A single recognized HTTPS artifact redirect receives no GitHub credential; unknown redirects, symlinks, encryption, extra entries, malformed UTF-8/JSON and size overruns are refused. The exact JSON SHA-256 must also match the selected transfer.

Current signed main/source/tree, canonical successful push CI, controls, original founder/comment/environment, exact producer bytes and canonical migration bytes are checked again. The original backend approval is validated historically at its export clock. Its mutation expiry is never refreshed. Consumption expires no later than 24 hours after the earliest original exported proof, within the existing web manifest window. This proves the provenance of the original reported backend gates; it does not re-execute private database/Storage/worker probes or infer continued private operation from old evidence.

The existing web workflow must still bind its own real independent source/QA reports and prepare its own exact founder approval comment before deployment credentials. Backend review facts contain no independent-attestation flags; importing them cannot invent a new passing review. Actual deployed five-role access, the critical learning/approval/intervention/reassessment/outcome journey, current denies and customer acceptance remain separate gates. Demo/tour/quick-login illustrations remain localhost-only; no production promotion or provider migration is introduced.

Implementation owners: `scripts/verification/backend-web-transfer.ts` and `backend-web-transfer-admission.ts`, with colocated controlled tests. The existing `cicd-release.ts` and `release.yml` consume `web-backend-bridge.ts` for four all-or-none manual staging inputs, canonical same-run selection/manifest/bridge outputs and fresh import before each web approval/build/deploy/verify boundary. Legacy automatic production admission remains separate. The web operator must supply its real independent report flags with exact original backend review task, digest, time and source facts; only the manifest digest is rebound to the actual imported native handover. Failed import never falls back to a manually supplied manifest. Verification emits only the exact public web deployment receipt; browser/domain acceptance remains a separate subsequent check.
