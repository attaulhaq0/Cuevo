# Automatic release after trusted CI

The founder requested an automatic, tested release process using the existing Vercel projects. This amends the manual trigger in the [release foundation](2026-10-02-ci-cd-and-release-boundaries.md); domain authority, hosted prerequisites and independent human/product approval remain required.

PRs run the full secret-free verification and aggregate required status. After review and merge, the canonical `main` push runs those checks again on the actual merged source. Only its completed successful same-repository `Cuevo verification` run can initiate production release admission. PR merge-tree results never substitute for the main source. Manual staging/production dispatch remains available for reviewed recovery and initial staged verification.

The release workflow reads the event as JSON through the existing validator. It accepts only a canonical main push with matching workflow path, repository, SHA and run ID. It never evaluates a branch, title or event value as shell code, downloads upstream artifacts, or checks out PR source using deployment credentials. The admitted commit is checked out explicitly in the protected environment. Current-main readback repeats after environment approval and immediately before upload; an obsolete successful build is refused. Automatic and manual production runs share a serialized concurrency group.

Before scheduling the deployment job, admission reads the existing GitHub environment, its explicit main-only branch policy, main protection and the separate required-signatures endpoint. It requires nonempty reviewed User/Team reviewers with self-review disabled, administrator environment bypass disabled, strict aggregate `required` status, CODEOWNER/stale-review/approval controls, enforced administrator rules, signatures and no declared PR bypass allowances. Unknown metadata or insufficient read access fails closed. An equivalent ruleset requires a separately reviewed adapter; it is not inferred. Actual `git rev-parse HEAD` must match the admitted SHA after checkout and before upload. The workflow guard rejects extra source checkouts, upstream artifact downloads and shell workflow-expression interpolation.

The existing strict dependency manifest, exact migration hashes, private grants/RLS/Storage/Realtime/recovery, worker transport and human environment approval remain mandatory. Vercel builds use public web configuration only; API secrets remain in the separate API project. App-local Vercel configuration disables automatic Git deployments so Git integration cannot race the verification gate. The compiled prebuilt artifact is hashed and checked before upload and its deployed project/team/SHA metadata and readiness are read back afterward. Production upload retains `--skip-domain`: the subsequent complete hosted actor/security/critical-flow checks and domain promotion remain unfinished release work, not an automatic health-only launch.

Fresh5October readback confirms existing `cuevo` and `cuevo-api` projects with no deployments. GitHub currently has no configured staging/production environments, release variables or secrets, and main is not protected. Sole CODEOWNER is the PR author. These controls and hosted prerequisite evidence must be established before this workflow can constitute a customer release; source YAML does not establish them. No account membership, protection, provider grants or live deployment changed in this work.

Current release metadata reads use the GitHub Actions token. If the repository does not grant supported read access to environment/administration metadata, admission refuses with a configuration/access review error. No privileged credential or token scope is invented here. Independent injected verification covers all four control endpoints, missing environment, source mismatch before network, stale main before upload and malformed/untrusted workflow variants; hosted execution remains unverified.

Docker remains isolated testing and packaging; it is not a laptop-dependent customer host.
