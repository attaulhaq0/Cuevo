## SQL boundary

The API verifies Supabase identity and current session, starts a database transaction, and sets local `app.actor_id` (Supabase subject UUID) and requested `app.school_id`. The session UUID is passed explicitly to its validation helper. Context is never copied from client roles or metadata. PostgreSQL runtime roles have no owner/BYPASSRLS privileges. Private `authorization` helpers use fixed search paths and current stored memberships/relationships; they cannot be reached by Data API roles. SQL references must quote the keyword schema: `"authorization".current_memberships()`.

`"authorization".current_memberships()` returns `membership_id`, `actor_id`, `school_id`, `school_name`, `display_name`, `role`, and `entitlement_codes text[]`. It uses the actor context and does not need a school context, supporting tenant selection. Disabled entitlements do not hide the membership but deny business rows.

`"authorization".is_current_session(session_id uuid)` checks a stored non-expired Supabase session belongs to the actor context, and that the Auth user is not deleted or banned. The API calls it before protected work; business RLS checks current school membership and entitlement. Runtime context is an API credential trust boundary, never a browser SQL interface.

`internal.begin_command(key text, command text, fingerprint text) -> jsonb` returns `state` NEW/IN_PROGRESS/COMPLETED and stored `response` for completed replay. Fingerprints are SHA-256 lowercase hex. Different input cannot reuse a key. `internal.finish_command(key, command, fingerprint, response jsonb)` stores the immutable command response inside the domain transaction.

`internal.append_audit(action, entity_type, entity_id uuid, request_id, outcome, metadata jsonb) -> uuid` stamps school and actor from current context. `internal.enqueue_event(type, entity_type, entity_id uuid, version integer, metadata jsonb, deduplication_key text) -> uuid` stores reliable publication in the same transaction. These are internal infrastructure tools; later domain services must validate purpose-specific metadata before calling them.

`cuevo_worker` can execute only `internal.claim_outbox(limit integer, lease_seconds integer)`, `internal.complete_outbox(id uuid, lease_token uuid)` and `internal.fail_outbox(id uuid, lease_token uuid, error_code text, retry_seconds integer)`. It has no raw learner or outbox-table privileges. Leases, retry caps and stale-token denial guard duplicate delivery.
