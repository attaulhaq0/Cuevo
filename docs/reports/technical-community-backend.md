# Safe community backend implementation

Date: 1 October 2026. Scope: Technical MVP Task4 backend. No frontend, credentials, runtime start, seed, reset or schema application was performed by this worker.

createCommunityController(identity,database) registers /v1/community rooms/roster/posts/reports/announcements/notifications and explicit room/member/post/reaction/report/moderate/restrict/announcement/read commands. Strict Zod inputs reject client actor/tenant authority and unknown fields. Current tenant/community entitlement, role, class enrollment/teacher assignment, explicit group membership and restriction scope are checked before stored replay. Teacher-owned groups and class discussion use the same implementation. Parents cannot read raw discussion or reporter details; current guardian context governs explicitly approved announcements.

Posts and replies are school text sources. Safe reactions are THANKS/HELPFUL/ENCOURAGE. Staff owner/admin moderation appends HIDE/RESTORE and MUTED/RESTRICTED/NONE records with explicit human confirmation/reason. Hidden content is projected as null. Reports create private staff queue and audit/event; serious safeguarding conclusions are never generated. New post/reaction/report actions are serialized and bounded to ten committed actions per minute; idempotent replay does not count again. Roster projects only current room displayName/role, leaving general people policies intact. No public profile/direct chat/attachments or automatic grade recognition is added.

Notifications are current authorized announcement pointers with immutable read receipts. All mutation/source/audit/outbox/receipt writes commit in one transaction. Root dispatches community.post_created/community.changed/moderation.reported events to internal.process_community_event(uuid,uuid); it resolves stored source/audit, validates lease, emits minimal private room invalidation and acknowledges with a persistent broadcast receipt. realtime.send swallows errors in the installed function, so the worker verifies matching stored realtime.messages output before committing acknowledgment. Broadcast payload contains no post body, names, grades or raw communication.

Current Supabase docs were retrieved through search_docs: [Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization), [Broadcast](https://supabase.com/docs/guides/realtime/broadcast) and concepts. Private channels require client private:true and project Allow public access disabled. SELECT RLS controls receiving; no client INSERT/Presence policy/grant is provided. JWT auth.uid/session_id and current auth.sessions expiry/owner/deleted/ban state plus stored room scope govern joins. Cached Realtime permissions refresh only on rejoin/new JWT, so API content access is rechecked on invalidation/reconnect; delivered bytes cannot be recalled. Actual join/revoked-cache behavior remains explicit integration evidence, never inferred from SQL policy presence.
