# Cuevo: a scalable K–12 learning experience

Date: 1 October 2026. Company: E Deviser. Product: Cuevo. Status: future experience proposal for the founder's whole-product review; no visual direction or application implementation selected.

Cuevo should grow as one learning system: school context makes learning possible; learning produces assessment and evidence; authorized evidence informs learner state and proposed support; people approve consequential actions; reassessment records what changed. The student experiences a helpful learning journey with an optional study buddy and motivating game expression. Adults experience a clear workbench for their own decisions. The same object identity, design tokens, controls and evidence grammar connect all five workspaces.

This proposal extends the [agentic direction](2026-agentic-experience-direction.md) and [full-screen atlas](2026-full-screen-atlas.md). The atlas compares 24 anchor screens in three visual worlds, totalling 72 frames. Those anchors are a design comparison, not complete rendered coverage of every nested page, locale, viewport or failure state. This document describes how the full LXP can expand without duplicating applications or claiming future capabilities already work.

## One system, composed for a current actor

Availability follows source07: school entitlement + academic configuration + current user authorization. The server resolves the school and actor, then checks entitlement, role permission, current relationship, programme and object scope as applicable on every protected query and command. Navigation reflects that result. A visible menu never supplies authorization.

The shell presents confirmed school context, the active role where role choice is supported, relevant academic period, locale, account/help and the current workstream. A future school or role switch must establish a new authorized context, invalidate the previous protected state and recheck objects before displaying them. It cannot be a cosmetic selector over already fetched data. A person with multiple roles receives deliberate workspaces, without merging all permissions into every page.

Use three navigation levels:

1. **Workspace destinations** organize the role's recurring work: learning, classes, evidence, family support or school controls.
2. **Object pages** preserve the selected course, learner, assessment, programme, group or review cycle with human-labelled breadcrumbs and a clear back destination.
3. **Related tabs and disclosures** organize facets of that same object. A tab changes the question about the object; a child page opens another object or a sustained task. Source detail, support diagnostics and confirmation dialogs open deliberately.

Future nested URLs should preserve a permitted object, tab, filters and pagination where appropriate, so browser back, refresh and deep links recover useful context. Opaque route keys may locate records internally; customer titles and labels use authorized names, class/year, subject, date and meaningful revision/status. Missing names show a localized unavailable state with a recoverable action. Same-name records use real context, never a shortened key suffix. Current logical views in the atlas are source observations; this proposal does not claim those future URLs exist.

The shared page anatomy is **context → primary action → working content → reason/evidence → optional assistance**. Dense tasks use an accessible list/table and selected detail; reading tasks use a readable lesson canvas; review tasks put proposal and evidence beside the decision. Do not fill remaining space with dashboard cards or charts without a decision. Each page declares actor, purpose, primary action, permitted context and empty/error/offline/denied/unknown behavior before implementation.

## A reusable learning and record pattern

[13 learning](../product/domains/13-LMS-LXP-FUNCTIONAL-SPEC.md) defines **Course → Unit → Lesson → Activity**. Keep that hierarchy throughout navigation, authoring, search, companion help and evidence links. A course belongs to authorized school/programme/class/subject context; its title does not substitute for that context.

| Object | Main page and related facets | Important action and boundary |
|---|---|---|
| Course | Overview, outline, approved resources, permitted work/feedback and course progress; staff planning and assessment facets | Continue a published lesson or manage assigned learning. Authoring and publishing are separate reviewed commands. |
| Unit | Purpose, lessons, approved objectives and available learning options | Open the next permitted lesson; retain the course breadcrumb and versioned reference context. |
| Lesson | Instructions/content, activities, permitted resources and feedback context | Learn and choose an available activity. Content, publication and availability must be current. |
| Activity | Instructions, attempt/work, submit or complete, feedback and history as supported by its type | Reading, practice, assignment, quiz, discussion and reflection reuse shared interaction patterns; each keeps its own domain lifecycle. |
| Assessment/submission | Native assessment context, own or assigned work, draft/review, feedback, released result and history | Preserve DRAFT → SUBMITTED → RETURNED → RESUBMITTED → CLOSED. Checked quiz feedback is not an authoritative academic grade. |
| Evidence/result | Named source, date, native result/criteria, review/release status, approved revision and related learning | Link the exact source. Academic release/correction remains deterministic, immutable, idempotent and audited. |
| Support/outcome | Approved learning action, why it was selected, completion/reflection, reassessment and observed comparison | Keep approved support separate from academic attainment. An observed change does not establish causal impact from AI. |

Assessments are related to learning when configured; do not force every activity into a grade. Preserve the distinction between assignment availability, assessment policy, approved academic reference and curriculum version. Publishing a new lesson or pack must not silently rewrite historical submissions, released results or their provenance.

The evidence pattern travels with the object: concise human source labels near the relevant claim; an explicit source drawer for the permitted date, reviewer, version/revision, rights/readiness and support limitations; technical source/run keys only inside deliberate provenance/support detail when necessary. Separate recorded fact, deterministic calculation, AI interpretation and human decision visibly. Missing evidence, stale context and an unavailable source are different states.

## Curriculum, jurisdiction and quality stay independent

A programme page exposes three distinct contexts: **what is taught and assessed** (curriculum), **which applicable local requirements apply** (jurisdiction), and **which evidence framework is under review** (quality/accreditation). A school may configure several programme instances and more than one overlay through the same data model. Do not make a programme label imply a jurisdiction or accreditation status.

An active academic context selects the exact approved pack version, programme/stage/subject scope, native terminology, assessment behavior and reporting policy. Source/rights/academic-review status and effective dates remain attached. Approved versions are immutable once used; a newer version enters an explicit review/activation process and historical records keep their original context. Inheritance from product defaults through pack, school, programme and course settings applies to non-authoritative defaults only; theme and teacher preferences cannot override official academic rules.

[06 pack acceptance](../product/curriculum/06-CURRICULUM-PACK-SPEC.md), [69 source lock](../product/curriculum/69-SOURCE-LOCKED-CURRICULUM-PROTOCOL.md), [50 coverage](../product/curriculum/50-CURRICULUM-COVERAGE-MATRIX.md) and [85 claims](../product/curriculum/85-ADVERTISED-SUPPORT-AND-CLAIMS-POLICY.md) govern readiness. Show the smallest verified programme/subject/version denominator with a plain explanation of review gaps. No inferred syllabus codes, grade boundaries, universal grade normalization or invented coverage percentage. UNKNOWN, REQUIRES_REVIEW and SOURCE_RESTRICTED stay truthful localized states with owner/review recovery paths.

The later quality workspace follows [22 quality](../product/quality/22-QUALITY-AND-ACCREDITATION-MODEL.md): framework/version → area/standard/indicator → evidence requirement → authorized evidence link → school self-study/action → review. Useful facets are requirements, evidence, gaps, actions, review and history. Reuse evidence links rather than copying learner files. Staff review and external decisions remain distinct; an evidence workspace does not establish accreditation or compliance.

## A functional study buddy and healthy game expression

The buddy is an optional contextual interface to learning, not a decorative home-only mascot. Its useful session is: choose available work → open the current lesson → attempt independently → consult permitted resources or returned feedback → choose teacher-approved practice → revise or reflect → confirm the saved/submitted receipt → see recorded recognition. It can explain navigation, remind the learner of their explicitly selected task and open authorized next steps. It must preserve the student's agency over submission and help-seeking.

Personalization under [12 personalization](../product/domains/12-PERSONALIZED-LEARNING.md) chooses among approved learning options using authorized evidence, current course context, teacher constraints and explicit learner choices. It can offer a scaffold, worked example, prerequisite review, practice, extension or reflection when available. It never changes the official curriculum, invents a mastery claim or infers personality, mental state, intelligence, family circumstances or protected traits.

Appearance, optional buddy name, language, interaction intensity, quiet mode and accessible presentation are voluntary user choices. Keep session-only choices honestly labelled until a durable preference/retention policy and persistence command exist. A future memory screen must show what was deliberately saved, its learning purpose, expiry and review/delete controls within the retention policy. Do not create hidden conversational memory from telemetry.

Live hinting, attempt explanation and tutoring require a **separate student-scoped workflow**; staff Teacher Insight cannot be exposed behind a student skin. Before activation, its specification must resolve:

- Purpose/actor: help the current learner understand a permitted lesson or approved practice; the student session is the actor.
- Data/context: minimum own lesson, approved resources, own attempt and permitted returned feedback; private academic/learner classification remains explicit. Exclude staff notes, peers, unrelated learner state and protected answer keys.
- Assessment-help policy: define permitted help by activity/availability state and teacher policy. Where the rule or source is absent, show help unavailable/review required instead of generating an answer.
- Tools/provider: schema-bound current-scope reads and allowed navigation/draft assistance, approved task/model/provider data policy, request/time/token/cost budgets and bounded retries; no credentials in the browser.
- Output: structured explanation/hint or approved-option recommendation, validated source citations, uncertainty and next action. A conversational transcript is not academic evidence or a grade.
- Governance: provenance, prompt/policy version, access audit, retention and abuse/report escalation; human review for generated material entering an official assignment or consequential support workflow.
- Failure: safe unavailable/insufficient-evidence/timeout response with ordinary learning still usable; no guessed official rules, automatic submission, grading, permissions or sensitive communication.

Game expression should make confirmed practice, revision and reflection visible through a personal journey, achievements and optional school-approved class challenges. Recognition comes from approved observed-action rules and idempotent XP transactions, separate from academic results and attainment. A reward animates after a confirmed receipt; it never assumes a failed/unknown submission succeeded. Opt-in class boards use permitted aliases, safe ties and period reset; personal progress remains available. No punitive ranking, guilt for absence, emotional dependence, rewards for surveillance volume or composite student-quality score. Reduced motion and hide/quiet choices preserve the same learning access.

## Contextual intelligence for mature workspaces

Adults use a contextual task rail beside the active object, with a full-width review page when a proposal needs sustained comparison. Teacher help might inspect current evidence and propose approved support; coordinator help might summarize a permitted programme gap; parent help might explain already approved feedback in plain language; admin help might prepare a policy-change preview. These are distinct purposes and role projections, not an unrestricted school chatbot. Only the current Teacher Insight & Intervention workflow is the MVP agent specified by [10 orchestration](../product/domains/10-INTELLIGENCE-ORCHESTRATOR.md); additional tasks need approved contracts and evaluations.

The shared task sequence is **goal → purpose/access check → permitted retrieval → evidence → structured proposal → human decision → deterministic command → receipt → follow-up**. Display actual execution state with plain labels such as checking available evidence, preparing a suggestion, ready for review, approved, recorded and awaiting follow-up. Do not simulate tools, percentage progress or background work. Show provider failure, insufficient context and cancelled/rejected states honestly.

Every proposal presents recorded facts separately from possible interpretation, why it appeared, authorized cited sources, missing evidence, proposed content/action and consequence, approval state and accept/edit/dismiss controls as permitted. Recheck current authorization, source versions and target state at decision time; an earlier retrieved snapshot is not permanent write permission. Consequential actions use domain commands with idempotency, audit and outbox. Unknown commit outcome preserves the original request and offers receipt recovery rather than silently creating another action.

[39 governance](../product/platform/39-SECURITY-PRIVACY-AND-AI-GOVERNANCE.md), [60 providers](../product/platform/60-AI-MODEL-AND-PROVIDER-ABSTRACTION.md) and [65 platform mechanics](../product/domains/65-AGENTIC-INTELLIGENCE-AS-A-PLATFORM.md) supply common purpose checks, authorized tools, model routing, schema validation, approval, provenance, failure and budget mechanisms. Education-specific tools and policies retain domain ownership. Never let AI release/change grades, grant access, publish official mappings, declare accreditation, contact a parent about a sensitive event or establish a safeguarding conclusion. Deterministic rules handle deterministic conditions.

## Tokens, themes, locale and responsive behavior

Select one visual world after reviewing the atlas, then derive semantic typography, space, radius, elevation, focus, density, surface/text/border/action/status colors and motion tokens in the shared design system. Role identity may change content density, illustration prominence and approved accent use; it does not create competing components or private hard-coded palettes. Light/dark themes preserve evidence, status and action semantics and independently verified contrast. A future tenant branding layer may change approved brand tokens without replacing navigation, accessibility or academic semantics.

Reuse accessible primitives for forms, dialogs, sheets, tabs, tables, timelines, source lists, proposals and receipts. Learning, evidence and intervention composites stay with their feature owner unless genuinely shared. Follow [36 design](../product/design/36-DESIGN-CONSTITUTION.md), [63 accessibility/RTL](../product/design/63-ACCESSIBILITY-RTL-I18N.md) and [79 interaction](../product/design/79-UI-UX-MOTION-AND-INTERACTION-SYSTEM.md).

English and Arabic are equal designs: translation keys, readable Arabic/Latin type, logical layout properties, meaningful directional mirroring, bidirectional text isolation and locale-correct numbers/dates/native grades. Keyboard focus, landmarks, labels, error associations, non-color status and reduced motion remain present across all themes. Use purposeful 120–280ms micro transitions where appropriate, with no animation-only information.

Desktop supports navigation + work canvas + optional context rail; tablet keeps the task and moves secondary context into a deliberate sheet or stacked region; mobile prioritizes the current action, readable content and reachable compact navigation, with the same evidence and controls available. Dense tables need a designed list/detail or labelled scrolling treatment. Review/approval must retain consequence and source context on mobile. Do not hide essential evidence to fit a viewport or cache protected learning offline by default.

For every nested destination, specify loading, empty, partial, unknown, stale, denied, error, reconnecting and mutation-outcome states as applicable. Never render denied access as no records or unknown coverage as zero. After session/relationship revocation, clear protected presentation and revalidate API, search, reports, files and private realtime scope. Offline drafts require an explicitly accepted low-risk policy and implementation.

## Growth through owners and public surfaces

Future scalability is an ownership and contract property, not a folder full of placeholder modules. Continue Next.js16 → NestJS/Fastify domain modules → PostgreSQL/Supabase → transactional outbox → worker. Add asynchronous reports/intelligence and bounded paginated retrieval as needed; introduce read models or independent deployment only with measured need and an ADR.

| Capability family | Existing owner to extend first | Boundary for later additions |
|---|---|---|
| Learning and academic truth | Web learning/academic; API school-learning/academic | Public learning/academic models and UI; immutable versioned contracts, native result and authorization tests. |
| Learner journey, support and buddy composition | Web home/progress/development/improvement; API learner-state/development/improvement | Buddy display can compose authorized public surfaces. A new student AI workflow needs a deliberate owner, policy/contract/evaluation and ADR when establishing a new boundary. |
| School/programme operations | Web school; API school/curriculum | Configuration-driven programme instances, independent overlays and current relationships; no school/programme-specific duplicate code. |
| Community, portfolio and private assets | Web community/portfolio; API community/portfolio/assets | Domain-scoped membership, moderation, exact sharing approval and authorized private bytes. |
| Later quality, broad reporting or workflow management | Add a real feature/domain only with its accepted work unit | README, codebase map, scoped instructions, public surfaces/contracts, migrations, discovery/configuration, acceptance tests and architectural decision in the same change. |

Next route files remain composition in `apps/web/app`; feature UI/models/copy/styles/tests remain together in `apps/web/features/<feature>`. Shell and cross-feature composition use documented `model.ts`, `api.ts`, `copy.ts`, `ui.tsx`; shared browser mechanisms never import feature internals. Reusable primitives/tokens use `@cuevo/ui`; shared packages never import app implementations. API domain behavior stays under modules, infrastructure under platform, worker jobs under jobs. No empty future domains, catch-all utility layer, copied source tree or mixed browser/server barrel.
