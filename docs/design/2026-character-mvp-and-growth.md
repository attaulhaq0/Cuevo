## MVP companion: a useful learning session

The MVP companion is a contextual presentation of supported work. It helps a student find and continue learning, read feedback, open an approved next step and understand a confirmed receipt. It does not require a model call to display a pose, show a saved state or route to an authorized activity. Deterministic conditions use deterministic presentation.

| Moment | Student task and primary action | Companion behavior and required evidence |
|---|---|---|
| Welcome/continue | Open an available course or resume the selected lesson | Neutral fox/owl with the current human-labelled course, lesson and real availability. Empty or denied states have their own recovery copy; no invented daily mission. |
| Lesson/resource | Read the current published lesson or permitted resource | Small reading companion beside an optional task tip. Explain supported navigation; do not insert guessed curriculum, fabricated examples or claims of adaptation. |
| Attempt/draft | Enter their own work, save a server draft or explicitly submit | Quiet presentation. Show validated draft content, actual save/submission state and receipt. No pose or animation claims completion while the outcome is unknown; the student retains submission control. |
| Returned feedback/revision | Read exact teacher-returned feedback, then revise where permitted | Task-related encouragement such as “Review your teacher's feedback” and an explicit revision action. Use neutral art, not worried/fail states or an inferred misconception/personality label. |
| Approved practice | Open a teacher-approved support activity or available differentiated option | Show why the activity is available, its teacher/source context and the student's allowed choice. A beacon pose can invite the action; it does not approve or generate the intervention. |
| Reflection | Complete the available reflection prompt and record it explicitly | Reading/neutral companion with plain language. Reflection text remains the learner's record, not a psychological assessment or hidden source of companion memory. |
| Recognition | Inspect confirmed practice/revision/reflection recognition | Optional coin pose after the recorded receipt. Show the approved action and period where meaningful; unknown/disabled points remain unavailable, not zero. |
| Reassessment/outcome | Open an assigned reassessment or permitted released feedback | Keep native academic results, source dates and teacher context separate from XP. A visual celebration does not claim mastery, causation or improved attainment without valid evidence. |

Preserve real record identity: course/lesson/activity title, teacher context where authorized, date, status and meaningful revision. Distinguish duplicate titles using real course/class/date context. Missing names have a localized unavailable state and a way to return, refresh or ask the appropriate school contact; an ID is never the primary label.

The optional companion panel may offer “Continue learning”, “Open feedback”, “Try approved practice”, “Reflect” or “Ask your teacher” only when the current contracts/policy support that action. Ordinary UI labels and approved teacher material remain code-native translations. The mascot cannot supply facts missing from the source, submit on the learner's behalf, reveal a quiz answer key, release grades, approve support, change access or promise an unsupported conversation.

## Choice, age and adult presentation

Provide explicit cosmetic controls: Fox/Owl/No character, quiet display and hide for this session. Describe their current duration plainly. Until accepted persistence and retention exist, hold these choices only in the current browser session's memory; do not silently store them across sign-out, another school context or another learner on a shared device. School authorization and learning access are independent of the display preference.

Selection uses the learner's expressed preference, not telemetry-derived “learning style”, personality, intelligence, mental state, motivation or gender. Age/stage may govern permitted presentation only through an explicit school policy using authorized school context. Do not invent age thresholds, infer age from activity, or lock older learners into a childish treatment. Provide a compact, mature option and no-character presentation for any permitted learner. Language, accessibility and reduced-motion preferences remain first-class regardless of mascot choice.

No emotional dependence or guilt: the character does not say it missed the learner, became sad through absence, needs loyalty, is a secret friend or is disappointed by a grade. Avoid coercive streak reminders, attention capture and scarcity rewards. Do not reward choosing a character or interacting with it more often. Recognition remains [09/15](../product/domains/09-HABIT-LEARNER-DEVELOPMENT.md) approved observed learning actions; no composite child-quality, character or intelligence score.

Teachers, coordinators, parents and admins share the design system and evidence grammar, with role-specific density and actions. The adult helper's value is the next useful permitted step and its evidence; a small optional illustration is secondary. Parent help uses exact approved child feedback/projections, never raw staff intelligence or internal habit signals. Admin presentation does not grant unrestricted student/pastoral access.

The shared student pack owns originals/provenance plus its required optimized derivatives; distinct responsive derivatives are documented outputs, not competing implementations. API orchestration, domain commands and worker jobs retain the [repository hierarchy](../architecture/repository-layout.md).

A reusable pack manifest separates character/pose identity from context and locale. It maps stable technical keys to optimized sources, intrinsic dimensions, accessibility/copy keys, accepted role/context use and explicit fallback. It contains no student records or academic rule mappings. Callers provide an allowed UI context derived from validated task state; they cannot request “low intelligence”, “worried learner” or an attainment-based emotional state. A missing/unapproved asset falls back to text and ordinary controls, preserving the task.

English/Arabic character names, control labels, task tips and state messages belong in translation resources. Do not bake them into images. Text-bearing excluded originals remain review evidence. Do not mirror every pose mechanically: direction-neutral characters and drawn text/symbols need semantic review, while layout uses logical properties and meaningful navigation direction. A theme changes semantic tokens and contrast, not the character's authority or academic semantics.

## Responsive frames, performance and accessibility

Use static optimized images as the default. Derive right-sized WebP/AVIF variants only after visual inspection of alpha, edges and color; retain a compatible accepted fallback. Set intrinsic width/height or an aspect ratio to prevent layout shift, declare responsive sizes, defer secondary poses and load only the active context's image. Do not preload all twelve 1024px originals, bundle the review contact sheet/archive into the app, or add video/WebGL just to animate a companion. Choose byte budgets after measuring the actual page and assets, then enforce the measured limits in verification.

At desktop widths, the current learning task owns the work canvas and the companion occupies a secondary margin/panel. At tablet widths, stack or deliberately open that context. At 390px and feasible 320px widths, use a compact optional character or hide its art while keeping the same controls, evidence and next action. Review at 768px, 1024px and 1440px as well. The character must never cover a form, consume the primary reading area, obscure feedback or require horizontal scrolling. Verify 200% zoom and Arabic line lengths.

Decorative poses use empty alternative text; the adjacent semantic heading/control conveys the task. A character-choice control has an accessible localized name and visible selected state independent of color. Meaningful status is text, with an appropriate live announcement only after real state changes. Keyboard focus remains visible and predictable; no animation-only cue, hover-only action or illustrated text substitutes for a label.

Use purposeful source79 micro transitions around 120–280ms where helpful for an actual receipt, opening context or selection. Respect `prefers-reduced-motion` and quiet/hide choices. Disable floating, pulsing, parallax, particle effects and glow amplification under reduced effects; a static pose and text give the same feedback. Persistent motion and auto-playing effects are not the default. Light/dark surfaces, non-color status, contrast and focus require their own verification.

## Live tutoring and memory: separately governed work

Live conversational help, interpretation of an attempt and durable memory are new student-scoped workflows. They cannot be activated by giving the existing staff Teacher Insight endpoint a fox avatar. Existing approved practice and exact teacher feedback remain useful while that work is unaccepted or unavailable.

Before a student AI workflow is implemented or activated, its accepted contract must resolve each requirement below:

| Requirement | Required decision/evidence |
|---|---|
| Purpose and actor | Help the current authenticated learner with the current permitted lesson/practice; explicit student initiation and school policy. Appearance selection grants no new tool rights. |
| Data classification and allowed context | Minimum own lesson, approved resources, own permitted draft/attempt and returned feedback. Exclude peers, staff-only notes, unrelated learner histories, secrets, protected answer keys and sensitive pastoral/family information. |
| Assessment-help policy | Define allowed hints/resources by activity, availability state and teacher policy. Missing source or ambiguous authorization yields unavailable/REQUIRES_REVIEW, never a guessed answer. |
| Tools and provider | Schema-bound current-scope reads and accepted assistance/navigation tools; approved model/provider/task/data-policy configuration under source60. Recheck tenant, entitlement, role, relationship/object scope as applicable on each protected request. |
| Output and provenance | Structured grounded explanation/hint/approved-option proposal, source citations, uncertainty and next action; prompt/policy/provider versions and run provenance. A transcript is not authoritative evidence, attainment or a grade. |
| Human control | No automatic submit, marking, curriculum mapping, permission change, sensitive communication or safeguarding conclusion. Consequential use routes to the accepted human-reviewed domain workflow. |
| Audit and failure | Purpose/access audit with minimized content, report/escalation rules, injection defense, schema/citation validation, bounded retry and safe timeout/insufficient-context/unavailable responses. Ordinary learning remains usable. |
| Cost and latency | Accepted per-request/session token, time and cost limits, cancellation and recovery behavior; actual progress labels only. Model choice stays replaceable through the platform registry. |
| Memory | Separate purpose-bound saved preference/learning-context schema, deliberate save/approval rules, visibility, expiry/retention, edit/delete controls, school/learner isolation and revocation/shared-device behavior. No hidden conversational memory inferred from telemetry or reflection. |

Durable cosmetic preferences are smaller than conversational memory but still need an explicit owner, authorized idempotent command, retention/privacy policy and clear controls. Do not store cross-school preference or memory by accident. Memory and AI proposals never overwrite native academic history or official curriculum. Reuse source65 mechanics for orchestration, tools, authorization, approval, audit and evaluations without creating a premature multi-industry platform or a broad “all learner data” retrieval endpoint.

Use source78 evaluations plus student-specific cases for protected answer keys, unsupported source, allowed/forbidden assessment help, peer/tenant leakage, prompt injection in lesson/attempt text, revoked access, rejected consequential proposal, timeout and memory isolation/deletion. Resolve provider data/region/contract and school age/consent/legal prerequisites explicitly before live/customer claims; fixture success does not satisfy them.
