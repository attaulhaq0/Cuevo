## Scope and authority

- Require exact local Cuevo Auth56321/DB56322/capture56324, entirely synthetic baseline and stopped owned apps before setup. Ordinary tests remain remote-model/PostHog/mail disabled.
- The supported initial owner approval admits one new confirmed administrator and one new school. Operator entitlements must explicitly include `school.context`, `school.operations`, `learning`, `assessment`, `curriculum`, `learner.state`, `improvement` and `portfolio`. Use only values accepted by the existing approval schema; do not grant another module merely for navigation.
- New teacher/student/guardian identities come from this school’s visible admin invitation/claim/password flow. A newly invited coordinator may be added for its existing academic approval role if required by current UI; use a new identity rather than the reference coordinator.
- Class/year/subject/teacher/student/guardian relationships use current normal School forms and confirmations, existing revision0/current update rules, exact receipt IDs and effective windows. No direct fixture insert may make those relationships “work.”
- Use a synthetic School Custom source that the teacher creates and the authorized reviewer explicitly approves and approves for the new course. Retain current source/review/technical limitations. Never reuse the fixed reference school’s `61000000...` objective, official syllabus codes or unchecked pack authority.
- Deterministic fixture mode must have explicit server fixture configuration and the newly admitted school’s normal approved intelligence policy. Unknown policy prevents analysis. The model proposes only; teacher decision creates practice. Missing observation is not zero and measured change remains non-causal.
- Parent gets only the explicit current child relationship, released source publication and exact approved portfolio revision. Private habit/intelligence/intervention state must remain absent from parent projection.
