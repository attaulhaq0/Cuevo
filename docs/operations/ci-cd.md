# Cuevo CI/CD operations

Owner: repository maintainer. This guide operates the existing [architecture](../product/platform/68-FINAL-TECH-STACK-AND-ADR.md) and [release decision](../decisions/2026-10-02-ci-cd-and-release-boundaries.md). The workflows are a foundation; deployment is unavailable until the exact external prerequisites are supplied and verified.

## Repository controls

Require `required` from Cuevo verification for the exact commit, human CODEOWNER review of sensitive changes, stale-review dismissal and signed commits. Protect main from direct agent pushes and bypass. Configure staging/production GitHub environments with main-only branch policy, independent required reviewers and no self-approval. These are GitHub settings; committing CODEOWNERS does not activate them. CI concurrency replaces obsolete branch runs. Release concurrency queues deployments per environment rather than interrupting a partially deployed release.

PR jobs use local generated synthetic identities only. They receive no production DB, migration, provider, Vercel or email secrets. The full technical job remains exclusive within its runner because source-replacement SQL and rollback fixtures cannot overlap runtime/browser operations. The 90-minute budget is an initial conservative allowance, not a hosted performance result. The source-frozen sequence and all required jobs must pass; a partial or skipped gate cannot become a release.

Sanitized `cuevo-safe-<sha>` artifacts contain only commit/run identity, source count and step statuses/durations. Never broaden upload paths to `.local`, recovery archives, logs, screenshots, traces, `.env`, synthetic accounts or source data. The full test logs may still require restricted access even on synthetic environments; do not add real pupil data to CI.

## Release manifest

The environment variable holds JSON version 1 validated by [cicd-contracts.ts](../../scripts/verification/cicd-contracts.ts). Required fields are:

- `environment`, `commitSha`, `ciRunId`, `verifiedAt` within 24 hours.
- `api`: a `container` descriptor has exact `origin`, `commitSha`, `imageDigest` (`sha256:`), `healthVerified: true`, `evidenceUrl`; existing manifests without kind normalize to container. A `vercel` descriptor requires `kind: "vercel"`, exact `origin`, `commitSha`, `projectId`, `teamId`, `deploymentId`, immutable `deploymentUrl` on vercel.app, matching `target` (`preview` or `production`), lowercase64character `artifactSha256`, `metadataVerified: true`, `healthVerified: true` and `evidenceUrl`. Strict variants reject mixed container/Vercel fields. Metadata attestations must reflect real readback for that source.
- `worker` requires an explicit `kind`. For `container`, include exact `origin`, `commitSha`, `imageDigest` (`sha256:`), `healthVerified: true`, `evidenceUrl`. For `supabase-edge`, include `commitSha`, `projectRef` matching `database.projectRef`, `functionName: "cuevo-worker"`, lowercase 64-character `artifactSha256` and `denoLockSha256`, `authVerified: true`, `queueRecoveryVerified: true`, `roleGrantsVerified: true`, `transportPrivateVerified: true`, `evidenceUrl`. The strict descriptors cannot mix container origin/image/health fields with Edge fields; a missing or unknown kind is refused.
- `database`: `projectRef`, the complete applied `migrations` array of `{version, sha256}`, `grantsVerified`, `rlsVerified`, `privateStorageVerified`, `privateRealtimeVerified`, `recoveryVerified`, `evidenceUrl`.
- `approval`: human `reviewer`, `basis` (`SYNTHETIC_STAGING` or `PRODUCTION_APPROVED`), `evidenceUrl`.
- `publicConfig`: `apiUrl`, `supabaseUrl`, `supabasePublishableKey`.

This is a reviewed operator evidence contract stored behind environment review; the current JSON does not provide a cryptographic signature. It contains no secrets. Each evidence link must resolve to the actual staged verification for this SHA. Booleans do not substitute for the tests/reviews they attest. Admission returns the worker descriptor and a readiness origin only for a container, and saves the original admitted manifest/CI identity in the ignored release directory. Verification re-admits that saved evidence, including its original 24-hour limit and exact release/migration identity, and requires the saved dependency receipt to match. It does not need the manifest or CI settings to be passed again by the verification step. Complete migration hashes must match checked-in immutable bytes, including the approved historical replay dependency for an empty environment. Existing environments apply only pending compatible migrations; never rewrite applied history or run a seed/reset against production.

## Sequence and rollback

1. Complete exact-commit CI and stage backend artifacts, compatible append-only migrations and private infrastructure. Snapshot/restore verification covers both database and private bytes.
2. Review the dependency manifest and environment permissions. Dispatch Cuevo reviewed web release from the exact current main SHA with its successful push CI run ID.
3. The workflow admits evidence, pulls only public web settings, builds and scans/hashes prebuilt output, uploads it and verifies raw team-scoped Vercel deployment metadata for project/team/SHA/target/URL plus web/API readiness. A container worker also receives a fresh `/health/ready` GET. Edge verification relies on the re-admitted, at-most-24-hour authentication, queue-recovery, role-grant and transport-privacy attestations; it sends no GET or signed POST to the worker function. CLI inspect summaries omit metadata and cannot prove source identity. A Vercel API descriptor receives a fresh team-scoped deployment-ID readback for exact project/team/source/target/URL before readiness; API and web projects must differ. API/container image digests, Vercel API prebuilt hashes/custom-origin bindings and Edge artifact/lock hashes remain operator evidence; Edge network execution is not established by this step. Production domains stay unpromoted.
4. Run the selected host's actual deployed worker health/outbox recovery, five-role Auth/current scope, protected Realtime, private file byte/download denial and source/academic/human-approval/reassessment smoke against the exact staged environment. Edge acceptance must prove signed wake rejection for missing/invalid/stale signatures, duplicate/concurrent admission, a real restricted TLS worker login and grants, private network queues, bounded claims/leases, lost-wake/expired-lease recovery and delayed/backoff work. Record these staged results before attesting or promoting domains. Live AI requires separately approved provider/data policy and budgets; deterministic fixture approval does not certify live quality.
5. Promote the verified production deployment only after that review. Record web deployment ID/SHA, API/container image digests or Edge project/function/artifact/lock identities, migration manifest, environment identities and approval/evidence. This final promotion is not implemented as an automatic shortcut.
6. On failure keep domains on the previous version. Roll back web/API/worker to compatible immutable artifacts. Database academic history is not reversed; use an approved forward repair or restore under the recovery runbook with explicit incident ownership. Never roll back an applied academic migration by deletion.

Agentic development follows the same checks: isolated patch proposals, source-locked curriculum/context, schema-limited tools, independent human review and the source78 deterministic eval harness. Credentials, migration access, deployment promotion, authoritative grades/access and real-pupil provider activation are outside automatic agent authority. Document new workflows with their purpose, actor, data classification, allowed context/tools, provenance, approval, audit and latency/cost/failure limits.
