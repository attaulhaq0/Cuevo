# Local process environment ownership

`initial-school.ts <approved-source.json> <original-key>` is a local operator-only school admission runner. It requires current operator and consenting first-admin Auth tokens in dedicated process environment, independently verifies both with the provider, and invokes only the private owner command on the guarded local target with stopped applications. It returns minimized admission identifiers; no token, password, Auth creation, public tenant endpoint or official curriculum default is introduced. The SQL records pre-school operator provenance and actual administrator consent before creating canonical school membership/audit/outbox. Unit/SQL/currentAuth/API proof remain distinct.

`local-school-accounts.ts enable|disable <operator-id> <reviewed reason>` is an explicit guarded local operator action. It verifies current Cuevo config/Auth/DB/capture targets and stopped application ports, stages a private API-only overlay before the SQL approval, and atomically publishes it after confirmed commit. Unknown commit never publishes; a postcommit write failure names the saved-approval/overlay boundary. `repair-overlay <operator-id>` reads the current exact approval under a lock and republishes its overlay without changing the approval revision or invalidating pending invitations. Ordinary CI/dev do not load `.local/school-account.env` automatically. Capture, recipient claim and production SMTP remain separate gates.

`source-paths.test.ts` exercises ordinary workspace API pack loading and bundled private worker spool paths independently of caller cwd. API artifacts set their private pack URL at compile time: process `./supabase/seed/curriculum/`, Vercel `../supabase/seed/curriculum/` from api/index.mjs. Source curriculum consumers resolve the owner-relative repository path. Compiled worker fixture evidence stays in `./.local/analytics/` under its artifact root; source evidence stays in repository .local/analytics. No browser/operator environment supplies these roots. Fixture capture remains local-only.

`build-artifacts.ts api-vercel` extends the existing API compiler with the hosted HTTP entry; API/worker Node process artifacts remain supported. Run `npm run build:api-vercel` from the root. It creates `.local/runtime-artifacts/api-vercel/.vercel/output` using Build Output API version3, one `api/index.func` with Node24/raw helpers disabled/60second outer duration and no static assets. Function files preserve the existing `supabase/seed/curriculum` working-directory location and include only compiler-owned runtime sources, manifest-verified pack files and a production dependency install from the projected exact registry/integrity lock. The operator's credentials, npm configuration, test fixtures and school seeds are excluded; package lifecycle scripts never run. The repository-pinned npm must be installed beside Node. Every prebuilt file, including dependencies and function configuration, has a digest in artifact.json; `prebuiltSha256` hashes their ordered path/digest list.

The deployer consumes that directory as its project working directory and uses `vercel deploy --prebuilt` only after the separate API project, exact source, CI, environment and backend/security evidence are approved. The artifact builder performs no deployment or model call. It must run without another API artifact builder because both own the same ignored output. `build-artifacts.test.ts` checks the prebuilt configuration, exact installed versions/byte hashes and actual compiled health/denial routes through a child Node HTTP server. Target-specific provider routing/private-byte behavior remains a hosted gate; local process checks do not establish it.

`environment.ts` constructs explicit child recipients for web/API/worker. It drops unrelated parent values and `NODE_OPTIONS`. Web build/server receives only three reviewed public settings and toolchain values. API receives its DB/Auth/Storage/provider settings; worker receives its restricted DB credential and explicit fixture analytics flag. This does not replace database authorization or protect a compromised operating-system account.

The dedicated CUEVO_AUTH_PROVISIONING_MODE/KEY/URL/PROJECT_REF/WEB_ORIGIN inputs reach only the API child when mode is explicitly LOCAL_SYNTHETIC. Disabled/absent modes never forward the key, and web/worker receive none of these fields. Server configuration independently verifies exact local origins/project and rejects hosted or production activation. No Storage credential fallback, automatic Auth executor or mail sender is introduced; ordinary source approval and durable effect authority remain required.

Hosted synthetic authority fields CUEVO_DEPLOYMENT_ENVIRONMENT/CUEVO_SYNTHETIC_PROJECT_REF/CUEVO_SYNTHETIC_WEB_ORIGIN and the optional reviewed CUEVO_DATABASE_TLS_CA are server-only API/worker recipients. The worker additionally receives SUPABASE_URL to validate its exact source project; it receives no Auth key. The Edge artifact bundles only the exact portable config/synthetic-runtime guard alongside the existing contracts/analytics source, and keeps the config entrypoint, validators, secrets and other packages outside its graph. These recipient and artifact cases are part of the existing verification steps.

`dev.ts` loads ignored root `.env.local` once and launches the installed Next/tsx executables with scoped environments and correct application working directories. Root `npm run dev` uses it; configured production-web build/browser verification uses the same mapper. Docker already declares each service's environment independently. Runtime fixtures live in `environment.test.ts` and are required by local-runtime/technical verification.

`foundry-environment.test.ts` verifies the reviewed API-only Foundry endpoint, credential, policy and limits. Web and worker inherit none of those fields; arbitrary public-prefixed model secrets remain excluded. The Foundry credential stays inherited in process/secret management, never written into local test settings or reports.

`process.ts` tracks only child processes created by this launcher and terminates their process trees on shutdown. Windows uses hidden bounded taskkill on the owned root before it exits; POSIX uses a dedicated process group. The real Windows child/grandchild regression verifies cleanup and preserves an unrelated process. A process not created by the launcher is rejected. POSIX behavior still requires its CI-platform execution.

The POSIX-specific stubborn-descendant test is skipped on Windows; Windows results do not establish Linux process-group behavior. If a Windows root has already unexpectedly exited, the launcher avoids killing a potentially reused PID; that recovery requires operator-owned process inspection. Normal launcher-initiated shutdown closes the owned tree before its root exits.

`drain-local-reference.ts` finishes guarded bootstrap by processing seeded outbox events through the same restricted bounded worker. It refuses non-Cuevo targets and failed or unfinished work. It never marks events complete through owner writes. This gives clean synthetic demo/Edge verification a settled source state before runtime startup; asynchronous user events remain the worker's normal responsibility.

Reference-drain metadata counts unresolved nonworker execution separately and refuses it before any general worker claim. Worker health must explicitly identify `WORKER` scope. Account Auth effects cannot be hidden by zero worker backlog or acknowledged as delivered through fixture drain. Existing global empty-queue recovery/competition preflights remain strict.

`posthog-local.ts` powers `npm run posthog:configure-local` after the administrator approves analytics in the synthetic school's privacy policy. It reads reviewed metadata from ignored `.local/posthog/config.json`, requires the exact local Cuevo project/ports and stopped app ports, verifies the active populated entirely synthetic school/current policy, then records a fresh database activation cutoff before atomically saving ignored `.env.posthog.local`. The command preserves existing keys and receipts; it never edits school policy or backfills preactivation events. `npm run posthog:configure-local -- --disable` deactivates that selected local school and replaces the overlay with disabled mode, retaining metadata and delivery history.

Only interactive `dev.ts` opts into this overlay after `.env.local`; the existing per-service recipients send its capture credentials only to the worker. CI, integration mode and `CUEVO_POSTHOG_LOCAL_OVERLAY=false` skip the overlay before reading it; the ordinary Playwright server explicitly sets that guard. Production-web, integration and aggregate verification do not load it, so ordinary verification remains disconnected from remote capture. After database bootstrap/reset, current policy and activation must be approved/configured again before new live synthetic collection. The pure local configuration tests exercise target/policy/population refusal, effect ordering, disabled retention, postcommit overlay failure and recipient exclusion without opening a database or network connection.
