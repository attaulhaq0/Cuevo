# Technical verification scripts

Outage-to-recovery handoff requires the exact validated Cuevo database's explicit running/non-restarting state and healthy native Docker health, followed by ordinary Supabase CLI status admission. SQL/API/Auth readiness alone can precede that Docker health result; the pinned CLI refuses it. The check observes starting/unhealthy/stopped/unknown states within a monotonic45second deadline (configuration maximum60seconds); each inspection/status command is capped by both its5/10second limit and the remaining deadline, and late results cannot admit readiness. Missing state stays unknown. Fixed state/CLI exit/reason metadata excludes health logs, credentials, status/stdout/stderr bodies and exception content; unknown CLI exits stay null. It never uses ignore-health-check, restarts another container or broadens target rules. Recovery writes ignored `provider-readiness.json` even when admission fails; outage retains the same minimized observations in its existing evidence. Injected tests cover delayed native readiness, no premature CLI request, target/malformed/CLI/inspection failure, explicit state and deadline refusal. Actual repaired CI recovery remains separate from these fixtures.

Account acceptance writes a unique report and durable recovery journal under ignored `.local/customer-readiness/account-phase/<run-id>`. The report must show each of the three required cases passed once, with no skipped, interrupted or flaky case. Owned processes close and all application ports must return confirmed TCP refusal before restoration. Exact before/after request ownership is saved before capture removal/database reset. Removal is read back; a cleanup failure still attempts restoration and fails the gate. An ownership journal failure blocks reset so original request pointers remain recoverable. Pure fixtures cover these boundaries; actual wrapper execution remains a separate required check.

The required browser row now uses `browser-complete.ts`: exact admission/recovery/inert tests run under explicit local account approval, their captured messages are cleaned by exact request ownership, and guarded bootstrap restores original identities/passwords and disabled controls before every ordinary browser journey. `browser-phases.json` retains each result; account/restore failure cannot become a passing browser gate. Dedicated config/test exclusions assign each critical file once through this required wrapper. Pure phase fixtures verify ordering/failure rules. [Decision](../../docs/decisions/2026-10-03-account-browser-acceptance.md).

The strict CI/CD manifest now records the actual API host. A legacy container API descriptor stays supported and is normalized to `kind: "container"`. A `kind: "vercel"` API requires exact project/team/deployment URL/ID, preview/production target, source SHA, prebuilt hash and reviewed metadata/readiness evidence; it cannot contain a container digest. Release verification re-admits the original24hour evidence and freshly reads team-scoped API deployment metadata before health requests, rejecting changed project, owner, deployment, target or source. API and web projects must be separate. Artifact hashes and custom-origin binding remain reviewed attestations; complete hosted authorization/private-byte/worker/security evidence remains required. `cicd-contracts.test.ts` uses an injected network sink and temporary receipts, never live deployment credentials.

technical-exit.ts runs the clean synthetic sequence and writes ignored.local/verification evidence. Missing/failed steps remain NOT_VERIFIED/FAILED. It intentionally resets only guarded local Cuevo synthetic state through the existing bootstrap; run after app processes stop and scheduled shared tests complete. Separate runtime/browser fixtures never run concurrently with rollback SQL source replacements.

The Edge verifier prints one final sanitized observation after cleanup and before its success/failure return. Only exact current check names, booleans, bounded counts/durations, fixed failure phases/codes and the artifact SHA are admitted; raw errors, HTTP bodies, process output, credentials and generated source identities are excluded. Cleanup failures stay explicit and any failure keeps the observation FAILED. This diagnostic does not alter execution, ownership, privacy or required gates, and the unsigned baseline HTTP observation alone never establishes a signed handler/source failure.

Browser performance and committed volume are explicit extra measurement windows: `customer-performance.spec.ts` and `customer-pilot-volume.spec.ts` skip unless their respective opt-in is set. Their normal production-web/API/worker runtime and guarded volume setup/restoration must run separately from rollback SQL. Ordinary frozen browser discovery includes the focused `customer-navigation-context` and `assessment-list-loading` regressions. `browser-pilot-volume-rules.test.ts` joins the existing migration-replay-rules row; adding its safety cases does not change the37row event identity. Actual browser-volume samples must pass before a pilot-scale claim; API population counts do not substitute for rendered evidence.

`posthog-evidence.ts` is an explicit operator-only export of that technical evidence, separate from school product-event capture. With the reviewed server-only PostHog configuration already available in the operator environment, run `node --env-file=.env.local --import tsx scripts/verification/posthog-evidence.ts --evidence-directory .local/verification/<run-timestamp>`. It requires LIVE_SYNTHETIC, QA, project393668 and exactly `https://us.i.posthog.com`; CI is refused. It sends one scalar-only `cuevo_verification_completed` event with synthetic QA/source/schema markers, required/passed/failed/unexecuted counts and source/evidence hashes. It never sends test bodies, stdout, source paths, credentials, school/person/child identifiers or academic content. The37-row sequence is version1 with a pinned name fingerprint; changes require explicit version review. Incomplete/failed evidence remains NOT_VERIFIED, and extra/unknown evidence fields or an inconsistent passing freeze fail closed.

The event describes its original frozen source snapshot. Current authored Git hashes separately establish exact source equality, Markdown-only changes, or historical source with runtime changes; JSON curriculum artifacts remain substantive. This comparison never reclassifies an old pass as a current-source pass. The runner records a start timestamp, so the exporter marks completion time NOT_RECORDED instead of inventing it. Retries use the same evidence-derived insert identity, three attempts and a three-second HTTP timeout. Console output contains only a minimized capture receipt; HTTP acceptance always leaves indexed PostHog readback NOT_VERIFIED until an operator separately queries the exact event. No export is scheduled automatically. `posthog-evidence.test.ts` uses temporary real Git/evidence directories and an injected HTTP sink; it neither reads operator credentials nor makes remote calls. See the [current-repository PostHog decision](../../docs/decisions/2026-10-02-posthog-current-repository.md).

recovery-drill.ts validates localproject5632x, stopped apps and restricted worker credentials, drains bounded outbox work, backs up/restores a scratch database and dedicated private Storage object, and verifies two-worker leases/expiry/retry. Privileged commands target only generated cuevo_recovery scratch databases/objects; no unrelated stack is stopped/reset. The preserved backup is ignored and may contain synthetic local credentials/data; do not commit or print it.

browser-secrets.ts scans configured browser static artifacts for actual server secret values without printing those values. build-workspaces.ts is the cross-platform build runner. rules.test.ts verifies target refusal and evidence completeness. Run only under synthetic local authorization; external provider/customer/official curriculum acceptance stays separate. Implementation report: docs/reports/technical-observability-recovery.md.

The configured Next build runs production mode after parent environment loading. playwright.production.config.ts starts the standalone production web build plus local fixture API/worker through production-runtime.ts and requires dependency readiness. It never reuses a dev server. This verifies production web assets in the synthetic environment and does not enable fixtures in a production school deployment.

Production and three-engine browser configs explicitly send SIGTERM with a ten-second launcher cleanup window; account/ordinary phases inherit the production config. The launcher stops only its owned detached API/worker/web children. Their output uses separate pipes forwarded with backpressure through the launcher, so a forced launcher termination cannot leave Playwright waiting for inherited stdout/stderr writers. Successful graceful cleanup and forced-kill EOF are separate: forced termination does not certify descendant/port cleanup, and subsequent exclusive runtime gates still refuse occupied services. The POSIX process fixture exercises installed Playwright launch/close with a detached owned writer in CI; Windows skips that platform-specific case. This changes shutdown behavior, not case/request/read budgets or source/authorization checks.

Child environments are selected by scripts/runtime/environment.ts. Web build/server receives only reviewed public configuration; API and worker receive their own credential consumers. Root local dev uses the same mapper. Arbitrary parent variables and NODE_OPTIONS do not flow into children. The runtime environment regression is a required technical verification step.

The exit runner requires a frozen authored-file snapshot, real API/SQL denial and private Realtime checks, runtime telemetry privacy, dependency audit and local database advisors. Recovery exercises restricted roles, forced RLS/grants and session denial against the restored database before cleanup. Browser tests include all-role keyboard, AX semantics, source37 viewports, English/Arabic RTL, reduced motion and 200% zoom-equivalent reflow. A passing automated reflow/AX check does not imply a manual assistive-technology certification.

`playwright.customer.config.ts` runs selected critical customer, Auth, draft/quiz and rubric journeys sequentially in Chromium, Firefox and WebKit. Exact compatible binaries must be installed; missing engines fail and cannot be claimed tested. It uses the same isolated production-web/local fixture runtime and never reuses a development server. The full role/accessibility matrix runs separately on the final build.

The current required sequence includes guarded real API/worker/database outage verification, the scratch restore, a clean browser seed, three-engine compatibility, the complete Chromium role/action/accessibility suite and a final fictional demo seed restore. Mutation windows never overlap. Clean browser seeding removes integration-created titles before customer language acceptance; the final restore prevents test-generated records appearing in a demonstration. All steps and the final source hashes must pass before completion. A manual incremental run does not replace this frozen sequence.

Integration journeys use a60second default total-case deadline; ordinary units retain15seconds and explicit case/setup limits remain authoritative. A journey can contain many separately bounded API/SQL operations. This runner deadline never changes the production five-second database statement limit or explicit latency/p95 assertions. Shared rollback-context cases use cooperative settlement before cleanup/next-case admission; a runner timeout is not handler cancellation.

Browser configs emit JSON result files under ignored `.local/customer-readiness` alongside HTML summaries. Ordinary `test-integration.ts` explicitly disables live intelligence opt-in, even if inherited from an operator environment; the separately authorized live command remains distinct. Integration results use the JSON reporter for scenario-level acceptance records. Final reports summarize these sanitized statuses; account credentials, request bodies and child content are never copied into committed evidence.

The required Edge runtime check starts only with applications stopped, private provider-owned transport grants, a disabled dispatch and an empty due queue. It uses the generated worker-owned artifact and actual local Supabase/Deno runtime, private signed wakes, canonical source processing, burst coalescing, rollback and one-minute recovery after a stopped worker. Local Kong is explicitly reloaded and tested through the same internal route after recreation; this is local gateway recovery evidence. Exact temporary Vault/job/event identities and container ownership are cleaned up. Reports contain only counts, statuses and timing; secrets and source bodies remain ignored. `npm run verify:edge` is not hosted or live-provider acceptance.

An unsigned HTTP status alone does not identify an active Cuevo handler: the baseline probe accepts only exact401`{code:"WORKER_AUTH_REQUIRED"}` as handler identity, and prints only status/fixed classification. Other responses remain UNKNOWN_RESPONSE without platform attribution. Before owned serving, unchanged active Cuevo gateway identity and every active Edge container remain independently guarded by Docker inventory; no active runtime is adopted or stopped. Post-start public and internal gateway probes require the same canonical handler denial, with response reads capped at512bytes/one second and unused bodies canceled. Pinned CLI gateway/default route failures cannot masquerade as handler readiness. The prior failed CI response was not retained, so its exact HTTP status/body remain unknown.

The aggregate places Edge verification after the guarded clean browser seed. Ordinary API suites can leave valid committed synthetic events; outage/recovery first process and verify that backlog through restricted source handlers. A clean seed supplies the Edge verifier's explicit isolation precondition. It does not silently delete failures to manufacture a worker result.

Recovery preserves two synchronized archives: the full backup includes scheduler configuration, while the scratch domain archive excludes only pg_cron and its cron schema because that extension cannot run in a second database. Domain/Auth/private Storage/migration fingerprints and restricted grants remain verified; scratch dispatch must be disabled. Scheduler restoration requires separate target verification and is never inferred from the full archive's presence or the scratch drill.

`foundry-smoke.ts` is an explicitly invoked, non-database synthetic Responses transport check. It inherits the approved credential, uses fixed synthetic native facts, performs one call without retries, and records only sanitized usage/status in ignored `.local/customer-readiness/foundry-smoke.json`. The ledger refuses a fourth call. The separate `customer-foundry-live-api.test.ts` requires both `CUEVO_REQUIRE_INTEGRATION=1` and `CUEVO_REQUIRE_LIVE_INTELLIGENCE=1`; it reserves one ledger call and exercises real Auth/controllers/private SQL, pending proposal, human approval, learner completion and native outcome in an isolated rollback tenant. Ordinary integration runs never activate this spend. Actual Azure billed cost is not supplied by Responses usage and remains unknown.

Both explicit Foundry writers share the test-only `customer-live-allowance.ts` helper. Only ENOENT permits a fresh zero ledger; malformed UTF-8/JSON or a count outside safe integer0..3 denies without rewriting it. An exclusive owned filesystem lock remains held through a synced atomic reservation, the one callback and identity/count-checked final receipt. A stale/concurrent lock requires operator review; attempts are never refunded or retried automatically. Final receipt failures preserve the consumed reservation and primary/cleanup errors. This coordinates cooperating local writers; it is not provider billing enforcement or power-loss durability certification. Thirty real temporary-file cases plus existing cleanup tests pass47offline checks without reading the actual ledger or invoking a model. The API journey receipt marks tenant cleanup PENDING_AFTER_ALL rather than claiming teardown before it runs.

`runtime-outage.ts` requires stopped applications and an exclusive local verification window. It validates project/ports, restricted API/worker credentials, and the exact `supabase_db_cuevo` PostgreSQL container on `cuevo-local`. Owned real API/worker subprocesses use the normal scoped environment mapper. A committed isolated synthetic tenant proves API restart/original-key replay, completion queued while the worker is stopped, worker restart/exact processed source projection, and database-only stop/start with readiness denial/recovery. Unrelated container IDs/running state/start timestamps are preserved. Related Supabase dependencies require an exact known Cuevo service name, `com.supabase.cli.project=cuevo` and `cuevo-local` network; their autonomous restart during the database outage is separately recorded and must finish running. Cleanup stops only owned processes, restores the targeted database if necessary and removes only the precisely guarded synthetic tenant's physical tables; no Auth identity is deleted. Docker inspection projects only reviewed identity/state/network fields and never reads environment values into diagnostic output. Sanitized checks and timings go to `.local/verification/runtime-outage/<timestamp>/evidence.json`. Run explicitly with `node --import tsx scripts/verification/runtime-outage.ts`; it never calls a model. `runtime-outage-rules.test.ts` verifies target refusal, related-project classification, unrelated-container preservation and receipt equality without restarting services.

The outage drill exercises controlled shutdown/restart and live database reconnect. It does not establish recovery from an unexpectedly exited Windows launcher with orphaned descendants, host power loss, disk corruption, sustained production load, or browser offline byte recall. Existing backup/restore and role/grant checks remain separate in `recovery-drill.ts`.

Container preservation distinguishes stable unrelated services from a service already observed restarting before the drill. The latter requires `Restarting=true`, `Status=restarting`, a positive restart count, a non-Cuevo project and a separate network; it is recorded as external state drift with preservation `NOT_ESTABLISHED`. All original IDs/name/project/network identities remain required, stable services must retain running state/start time, and every explicit Docker lifecycle command is guarded and recorded as targeting only the validated Cuevo database. This does not claim an already failing foreign service remained unchanged or authorize repairing it. A foreign service that was stable before the drill and changes still fails verification.
